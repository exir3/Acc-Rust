# نرم‌افزار حسابداری (Acc-Rust)

نرم‌افزار حسابداری دسکتاپ برای Windows با رابط کاربری HTML/CSS/JavaScript و هستهٔ Rust + SQLite (Tauri 2).

## امکانات اصلی

- تعریف گروه حساب، حساب کل، معین و تفصیلی ۱ با پیمایش سلسله‌مراتبی
- ثبت، ویرایش، دائمی‌سازی و حذف سند حسابداری
- کنترل تراز، تاریخ شمسی، حساب‌های فعال و سال مالی باز
- گزارش دفتر کل، تراز آزمایشی، صورت سود و زیان و ترازنامه
- ورود و خروجی Excel برای حساب‌ها و اسناد
- پشتیبان‌گیری، اعتبارسنجی فایل پشتیبان و بازیابی با نسخهٔ ایمنی
- گزارش رویدادها (audit log) و کنترل هم‌زمانی ویرایش

## پیش‌نیازها

- Windows 10/11
- [Node.js](https://nodejs.org/) 20 یا جدیدتر
- [Rust](https://rustup.rs/) با toolchain پایدار (حداقل نسخهٔ تعریف‌شده در `src-tauri/Cargo.toml`)
- WebView2 (در Windows 11 پیش‌نصب است)

## اجرای پروژه

```bat
npm ci
npm run dev
```

یا با اسکریپت‌های ویندوزی:

```bat
run.bat            :: ساخت debug و اجرا
run.bat release    :: ساخت release و اجرا
run.bat cleanup    :: پاک‌کردن کش ساخت
```

## ساخت نسخهٔ دسکتاپ

```bat
build.bat            :: exe قابل حمل (پیش‌فرض)
build.bat installer  :: exe + نصاب NSIS
build.bat all        :: exe + نصاب NSIS
```

معادل دستورهای npm:

```bat
npm run build
```

خروجی‌ها در `src-tauri/target/release/` و نصاب NSIS در
`src-tauri/target/release/bundle/nsis/` ساخته می‌شوند. اسکریپت `build.bat`
خروجی‌ها را در پوشهٔ `dist/` نیز کپی می‌کند.

## آزمون‌ها و بررسی کد

```bat
npm run check:js
npm test
npx playwright install chromium
npm run test:e2e
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --all-features
cargo test --manifest-path src-tauri/Cargo.toml
```

- `npm run check:js` فقط صحت نحوی فایل‌های JavaScript را بررسی می‌کند.
- `npm test` آزمون‌های واحد فرانت‌اند را با test runner داخلی Node اجرا می‌کند.
- `npm run test:e2e` آزمون‌های واقعی مرورگر را با Playwright و Chromium اجرا می‌کند.
  بار اول باید Chromium را با `npx playwright install chromium` نصب کرد. این آزمون‌ها
  رابط کاربری را روی یک سرور استاتیک محلی (`scripts/serve-ui.mjs`) باز می‌کنند و
  تعامل انتخابگر حساب، فرم تعریف حساب و چرخهٔ کامل سند (ساخت، ذخیره، بازکردن،
  دائمی‌سازی و حذف) را در DOM واقعی بررسی می‌کنند. بک‌اند Tauri در این آزمون‌ها با
  یک mock درون‌صفحه‌ای (`tests/e2e/mock-tauri.js`) شبیه‌سازی می‌شود؛ منطق واقعی
  بک‌اند همچنان با آزمون‌های Rust پوشش داده می‌شود.
- آزمون‌های Rust شامل قواعد سند، سال مالی، گزارش‌ها، Excel، پشتیبان‌گیری و مهاجرت پایگاه داده هستند.

## ساختار مخزن

| مسیر | توضیح |
| --- | --- |
| `ui/` | رابط کاربری Tauri (HTML، CSS و JavaScript) |
| `src-tauri/src/commands/` | پل فرمان‌های Tauri بین UI و منطق Rust |
| `src-tauri/src/db/` | اتصال SQLite، schema، مهاجرت، سال مالی، پشتیبان‌گیری و حساب‌ها |
| `src-tauri/src/vouchers/` | اعتبارسنجی، ذخیره، حذف، انتقال و گزارش‌های سند |
| `src-tauri/src/report/` | قالب‌بندی و محاسبات گزارش‌های چاپی |
| `src-tauri/src/excel/` | ورود و خروجی Excel |
| `scripts/` | ابزارهای بررسی، آزمون و سرور استاتیک UI |
| `tests/` | آزمون‌های واحد فرانت‌اند (`tests/e2e/` آزمون‌های Playwright) |
| `Docs/` | مستندات و گزارش بررسی فنی |

## معماری

```text
HTML/CSS/JS (Tauri WebView)
        │  invoke(...)
        ▼
src-tauri/src/commands/*.rs
        │
        ▼
src-tauri/src/vouchers, db, report, excel
        │
        ▼
SQLite (فایل پایگاه دادهٔ کاربر)
```

رابط کاربری هیچ منطق حسابداری حساسی را به‌تنهایی تعیین نمی‌کند؛ اعتبارسنجی نهایی
حساب‌ها، تراز سند، تاریخ، سال مالی و دائمی‌بودن سند در Rust و triggerهای SQLite
انجام می‌شود.

## مدل حساب‌ها

- **گروه حساب**: دسته‌بندی بالای حساب‌ها (مثلاً دارایی، بدهی، درآمد، هزینه).
- **حساب کل** (سطح ۱): کد چهاررقمی.
- **حساب معین** (سطح ۲): فرزند مستقیم حساب کل.
- **تفصیلی ۱** (سطح ۳): فرزند مستقیم حساب معین و متعلق به همان گروه حساب.

هر ردیف سند یک حساب پایه (کل یا معین) و به‌صورت اختیاری یک تفصیلی ۱ دارد.
بک‌اند و trigger پایگاه داده بررسی می‌کنند که تفصیلی انتخاب‌شده فرزند مستقیم همان
معین و هم‌گروه با آن باشد.

## اسناد و سال مالی

- سند باید حداقل دو ردیف داشته باشد و مجموع بدهکار و بستانکار آن برابر باشد.
- مبلغ هر ردیف و تعداد ردیف‌ها محدودیت دارند.
- ثبت و ویرایش در سال مالی بسته یا نهایی‌شده مجاز نیست.
- سند دائمی و ردیف‌های آن با triggerهای SQLite در برابر تغییر و حذف محافظت می‌شوند.
- ویرایش هم‌زمان با `expected_updated_at` و ذخیرهٔ تکراری با کلید idempotency کنترل می‌شود.
- بازگشایی سال مالی نهایی‌شده نیازمند دلیل و تأیید صریح است و در audit log ثبت می‌شود.

## پشتیبان‌گیری و بازیابی

پیش از بازیابی، از پایگاه دادهٔ فعال یک نسخهٔ ایمنی ساخته می‌شود. فایل پشتیبان از
نظر سلامت SQLite، ساختار جداول، کلیدهای خارجی و اعتبار اطلاعات حسابداری بررسی
می‌شود. در صورت شکست بازیابی، برنامه تلاش می‌کند نسخهٔ قبلی را بازگرداند.
تعداد نسخه‌های پشتیبان نگهداری‌شده محدود است تا پوشهٔ پشتیبان بی‌رویه رشد نکند.

## CI

workflow در `.github/workflows/ci.yml` چهار job دارد:

1. **verify**: نصب قطعی وابستگی‌ها با `npm ci`، بررسی نحوی JavaScript، آزمون‌های
   واحد فرانت‌اند، بررسی قالب‌بندی Rust، Clippy و آزمون‌های Rust.
2. **ui-e2e**: نصب Chromium و اجرای آزمون‌های واقعی مرورگر با Playwright؛ در صورت
   شکست، گزارش و trace آزمون‌ها به‌عنوان Artifact آپلود می‌شود.
3. **security-audit**: اجرای `npm audit --audit-level=high` و `cargo audit`.
4. **desktop-build**: فقط پس از موفقیت `verify`، `ui-e2e` و `security-audit` اجرا
   می‌شود. ساخت دو مرحله‌ای است: ابتدا `tauri build --no-bundle` فایل اجرایی را
   می‌سازد، در صورت وجود گواهی همان فایل اجرایی امضا می‌شود، سپس
   `tauri bundle --no-binary-patching` نصاب NSIS را از فایل امضاشده می‌سازد و در
   صورت وجود گواهی نصاب را نیز امضا می‌کند. در پایان `signtool verify /pa /v`
   اعتبار هر دو امضا را بررسی می‌کند. بدون گواهی، Artifact با نام
   `windows-installer-unsigned` منتشر می‌شود؛ برای انتشار رسمی، اجرای
   `workflow_dispatch` با `release: true` در نبود گواهی شکست می‌خورد. فایل
   `release-metadata.json` شامل hash و اطلاعات گواهی در کنار نصاب آپلود می‌شود.
