### ۵-۱. دریافت تمام درخت حساب‌ها در یک درخواست

این کار برای جلوگیری از درخواست‌های تکراری و فراهم کردن جستجو و پیمایش درخت حساب‌ها قابل توجیه است؛ اما وقتی تعداد حساب‌ها بسیار زیاد شود، حجم اطلاعات منتقل‌شده افزایش می‌یابد.

- حالت جستجو و پیمایش پیشرفته: اطلاعات شاخه انتخاب‌شده و فرزندان آن دریافت شود.

در صورت وجود تعداد بسیار زیاد حساب، دریافت اطلاعات باید صفحه‌بندی یا مبتنی بر شاخه حساب باشد.

### ۵-۲. بازسازی کامل جدول پس از هر بار فیلتر

```
grid.innerHTML = trialGridMarkup(
```

یعنی با تغییر فیلتر یا انجام جستجو، تمام HTML جدول از ابتدا تولید و جایگزین می‌شود.

برای مثال، اگر ۲۰ هزار حساب در جدول نمایش داده شوند و جدول ۱۰ ستون داشته باشد، تعداد بسیار زیادی عنصر DOM ایجاد خواهد شد.

### ۵-۳. دوباره‌کاری در فیلتر کد حساب

در حال حاضر محدوده کد حساب هم در Rust و هم در JavaScript بررسی می‌شود.

در Rust از مسیر سلسله‌مراتبی حساب استفاده شده است؛ اما در JavaScript تابع `trialCodeSegments()` با طول بخش‌های کد حساب مقایسه انجام می‌دهد.

در کدینگ‌هایی که ساختار کد حساب‌ها یکنواخت نیست، این دو روش ممکن است خروجی یکسانی نداشته باشند.

پیشنهاد من این است که منطق تعیین محدوده حساب فقط در یک لایه، ترجیحاً Rust، اجرا شود و فرانت‌اند صرفاً نتیجه را نمایش دهد.

برای این موضوع باید آزمون‌هایی با کدهای حساب نامنظم، کدهای والد و فرزند و حساب‌های مشابه نیز اضافه شود.

### ۵-۴. نبود وضعیت پیشرفت و امکان لغو تولید تراز

در `pages-core.js` هنگام بارگذاری صفحات، یک وضعیت عمومی بارگذاری نمایش داده می‌شود.

در فرمان تولید تراز نیز برخلاف ورود گروهی اسناد، سازوکار گزارش پیشرفت و لغو عملیات وجود ندارد.

این موضوع به‌خصوص وقتی پردازش چند ثانیه یا بیشتر طول بکشد، باعث می‌شود کاربر تصور کند برنامه هنگ کرده است.

### ۶-۱. اتصال واحد و قفل Mutex

همان‌طور که اشاره شد، در ساختار فعلی برنامه فقط یک اتصال SQLite نگهداری می‌شود.

تابع `with_conn()` پیش از اجرای عملیات، قفل اتصال را دریافت می‌کند و تا پایان اجرای تابع آن را در اختیار نگه می‌دارد.

این مسئله دو پیامد دارد:

اول، اجرای هم‌زمان عملیات گزارش‌گیری و سایر عملیات دیتابیس محدود می‌شود.

دوم، در زمان اجرای یک گزارش سنگین، درخواست‌های دیگر ممکن است منتظر بمانند.

برای مثال:

فرض کنیم تراز آزمایشی در حال محاسبه است و کاربر در پنجره دیگری درخواست مشاهده سند حسابداری را ارسال می‌کند. درخواست دوم برای دسترسی به همان اتصال باید منتظر بماند.

### معماری پیشنهادی

رابط کاربری Tauri / WebView2

پنجره اصلی، فرم اسناد، گزارش‌ها و چاپ

لایه فرمان‌ها و مدیریت درخواست‌ها در Rust

اعتبارسنجی، کنترل دسترسی، مدیریت عملیات و لغو درخواست

اتصال نوشتن

ثبت و ویرایش سند، حذف، مهاجرت

اتصال‌های خواندن

تراز، دفتر کل، روزنامه و گزارش‌ها

SQLite با WAL

یک پایگاه داده مشترک با کنترل سازگاری و تراکنش‌ها

پیشنهاد من این است که یک Connection Pool محدود برای عملیات خواندن ایجاد شود.

برای شروع، ۲ تا ۴ اتصال خواندن مستقل را بررسی کنید. این تعداد یک پیشنهاد اولیه برای آزمایش است، نه عدد قطعی.

اتصال‌های خواندن باید:

- فقط به همان فایل دیتابیس فعال متصل باشند.
- در صورت نیاز با مجوز Read-only باز شوند.
- `query_only` داشته باشند.
- تنظیمات مناسب WAL و `busy_timeout` را دریافت کنند.
- هنگام Restore، جایگزینی یا تغییر پایگاه داده به‌درستی متوقف و بازسازی شوند.

در این معماری، نوشتن همچنان از مسیر کنترل‌شده فعلی انجام می‌شود و محدودیت‌های مالی و تراکنش‌ها حفظ می‌شوند.

نکته: توصیه نمی‌کنم برای افزایش سرعت، `synchronous` را غیرفعال کنید یا مقدار آن را بدون ارزیابی ریسک اطلاعات حسابداری کاهش دهید. تنظیم فعلی `FULL` در این پروژه تصمیم محافظه‌کارانه و مناسبی است.

### ۶-۲. تنظیمات فعلی SQLite

در `connection.rs` تنظیمات زیر مشاهده شد:

| تنظیم              | مقدار فعلی | ارزیابی                                          |
| ------------------ | ---------- | ------------------------------------------------ |
| journal_mode       | WAL        | مناسب                                            |
| foreign_keys       | ON         | ضروری                                            |
| busy_timeout       | 5000 ms    | مناسب                                            |
| cache_size         | 32 MB      | قابل آزمایش                                      |
| temp_store         | MEMORY     | مناسب برای برخی گزارش‌ها، همراه با ریسک مصرف RAM |
| mmap_size          | 256 MB     | قابل آزمایش                                      |
| journal_size_limit | 64 MB      | قابل حفظ                                         |
| synchronous        | FULL       | پیشنهاد می‌شود حفظ شود                           |

پیشنهادهای تکمیلی:

1. اجرای `PRAGMA optimize` پس از ورود گروهی اطلاعات حجیم و تغییرات عمده ساختار پایگاه داده بررسی شود.
2. مصرف حافظه در زمان اجرای Queryهای دارای Group By و Sort اندازه‌گیری شود.
3. افزایش Cache فقط پس از اندازه‌گیری مصرف RAM انجام شود.
4. اندازه فایل اصلی SQLite و فایل WAL در حجم‌های مختلف اطلاعات ثبت شود.

## ۷. بررسی سایر گزارش‌های مالی

علاوه بر تراز آزمایشی، در گزارش دفتر کل نیز یک نقطه مهم برای بهینه‌سازی وجود دارد.

### ۷-۱. گزارش دفتر کل

فایل:

`src-tauri/src/vouchers/reports/ledger.rs`

در محاسبه مانده افتتاحیه، اطلاعات بدهکار و بستانکار ردیف‌ها از SQLite خوانده شده و در Rust با حلقه جمع می‌شوند.

همین موضوع برای محاسبه مانده سطرهای قبل از صفحه جاری نیز اتفاق می‌افتد.

به‌خصوص قسمت دوم اهمیت دارد.

فرض کنید یک حساب ۲۵۰ هزار ردیف گردش دارد و کاربر می‌خواهد صفحه‌ای را در انتهای گزارش مشاهده کند.

در روش فعلی، سیستم باید ردیف‌های قبلی را با توجه به `OFFSET` بخواند و جمع آن‌ها را دوباره در Rust محاسبه کند.

این کار برای صفحات عمیق پرهزینه است.

راهکار اصلاح:

برای مانده افتتاحیه از تجمیع مستقیم SQLite استفاده شود:

```
SELECT
    COALESCE(SUM(l.debit), 0),
    COALESCE(SUM(l.credit), 0)
FROM voucher_lines l
JOIN vouchers v ON v.id = l.voucher_id
WHERE ...
```

برای مانده پیش از صفحه نیز به‌جای انتقال تمام ردیف‌های قبلی به Rust، محاسبه جمع در SQL انجام شود.

در گام بعد، استفاده از Keyset Pagination یا محاسبه مانده با Window Function بررسی شود.

این اصلاح در گزارش‌های دفتر کل با گردش بالا می‌تواند تأثیر زیادی داشته باشد.

### ۷-۲. دفتر روزنامه و لیست اسناد

وضعیت این بخش‌ها نسبتاً بهتر است.

در نسخه فعلی:

- گزارش دفتر روزنامه صفحه‌بندی ۵۰۰ ردیفی دارد.
- لیست اسناد صفحه‌بندی ۲۰۰ ردیفی دارد.
- گزارش دفتر کل نیز قابلیت دریافت صفحه دارد.

اما در تابع جستجوی مشترک `src-tauri/src/vouchers/query.rs` جستجو روی شرح سند، نوع سند، نام حساب، کد حساب و شرح ردیف از الگوهای `LIKE '%...%'` و جستجوی وابسته به هر سند استفاده می‌کند.

مشکل این است که چنین جستجوهایی با ایندکس معمول B-Tree به‌خوبی قابل بهینه‌سازی نیستند.

- ایجاد ساختار جستجوی مستقل برای شرح سند، شرح ردیف و عنوان حساب.
- نگهداری نسخه نرمال‌شده متن برای سازگاری حروف فارسی و عربی.
- به‌روزرسانی اطلاعات جستجو با Trigger یا در همان تراکنش ثبت و اصلاح سند.

این پیشنهاد به‌خصوص برای جستجوی متنی در صدها هزار ردیف اهمیت دارد.

7. در صورت لغو یا بروز خطا، تراکنش اصلی Rollback شود.

1. خواندن مرحله‌ای Excel

4. تهیه پیش‌نمایش و گزارش خطا
5. تأیید کاربر

### ۸-۲. اجرای مکرر دستورات SQL در حلقه ورود اسناد

در `vouchers/import.rs` برای هر سند و هر ردیف، عملیات SQL تکرار می‌شود.

به‌عنوان نمونه:

```
for (index, line) in lines.iter().enumerate() {
    tx.execute(
        "INSERT INTO voucher_lines ...",
        params![...],
    )?;
}
```

همچنین برای ثبت هر سند:

```
tx.execute(
    "INSERT INTO vouchers ...",
    params![...],
)?;
```

پیشنهاد من استفاده از `prepare_cached()` یا آماده‌سازی یک‌باره دستورات و استفاده مجدد از آن‌ها در حلقه است.

نمونه:

```
let mut insert_line = tx.prepare_cached(
    "INSERT INTO voucher_lines
     (voucher_id, row_no, account_id, account_code,
      detail1_code, description, debit, credit)
     VALUES (?1, ?2, ?3, ?4, ?5, ?6, ?7, ?8)"
)?;

for (index, line) in lines.iter().enumerate() {
    insert_line.execute(params![
        voucher_id,
        index as i64 + 1,
        account_id,
        line.account_code,
        line.detail1_code,
        line.description,
        line.debit,
        line.credit
    ])?;
}
```

این نمونه برای نشان دادن روش است؛ پیاده‌سازی نهایی باید با اعتبارسنجی حساب و Triggerهای موجود سازگار باشد.


این تابع برای تاریخ سند، سال مالی متناظر را از دیتابیس پیدا می‌کند.

اگر فایل شامل ده‌ها هزار سند و فقط یک یا دو سال مالی باشد، تعداد زیادی درخواست تکراری برای یافتن سال مالی انجام می‌شود.

راهکار:

سال‌های مالی یک بار در ابتدای تراکنش خوانده شوند و بر اساس محدوده تاریخ، سال مالی هر سند در حافظه تعیین شود.

در صورت نیاز به ایجاد سال مالی جدید نیز عملیات ایجاد فقط یک بار و به‌شکل کنترل‌شده انجام شود.

### ۸-۴. استفاده از اطلاعات حساب در هنگام ورود

در اعتبارسنجی اسناد، حساب‌ها به شکل گروهی بارگذاری می‌شوند؛ این قسمت طراحی مناسبی دارد.

با این حال، در مرحله ورود نهایی، بهتر است شناسه حساب‌ها برای همه کدهای موجود در فایل از قبل در یک `HashMap` نگهداری شود تا در حلقه ثبت ردیف‌ها احتیاج به جستجوی تکراری حساب نباشد.

همچنین بهتر است شماره سندها و سال مالی مربوط به هر گروه از اسناد از قبل آماده شوند.

### ۸-۵. ثبت اطلاعات Audit برای هر سند

در حال حاضر برای هر سند واردشده، `voucher_snapshot()` اجرا و اطلاعات قبل و بعد در گزارش رویدادها ثبت می‌شود.

این کار از نظر حفظ سوابق حسابداری ارزشمند است، اما در ورود بسیار حجیم هزینه پردازشی و I/O ایجاد می‌کند.

پیشنهاد می‌کنم اطلاعات Snapshot برای سندهای واردشده تا حد امکان از اطلاعات معتبر موجود در حافظه ساخته شود، نه با خواندن مجدد تمام اطلاعات سند از پایگاه داده.

البته نباید برای افزایش سرعت، سابقه حسابرسی یا امکان بازسازی تغییرات سند حذف شود.

نکته مثبت: ورود گروهی فعلی از یک تراکنش برای کل عملیات استفاده می‌کند و قابلیت لغو و Rollback دارد. این ویژگی باید در هر بازطراحی حفظ شود.

## ۹. بررسی کیفیت آزمون‌ها و اطمینان از صحت محاسبات حسابداری

### ۹-۱. نبود آزمون عملکرد با ۳۰۰ هزار ردیف

در تست‌های Rust، آزمون‌های مربوط به تراز، مانده افتتاحیه، گردش دوره، حساب‌های والد و فرزند و محدوده کد حساب وجود دارند.

اما تست‌های موجود عمدتاً برای مجموعه‌های کوچک طراحی شده‌اند.

برای مثال آزمون:

`trial_balance_splits_opening_and_period_activity`

با تعداد محدودی سند، صحت تفکیک مانده افتتاحیه و گردش دوره را بررسی می‌کند.

این آزمون‌ها برای بررسی منطق حسابداری مناسب هستند؛ ولی اثبات نمی‌کنند که برنامه با ۳۰۰ هزار ردیف نیز عملکرد مناسبی دارد.

### ۹-۲. آزمون‌های پیشنهادی

### ۹-۳. چه چیزهایی باید اندازه‌گیری شوند؟

صرفاً ثبت زمان کلی اجرای تابع تراز کافی نیست.

پیشنهاد می‌کنم این زمان‌ها مستقل اندازه‌گیری شوند:

| شاخص                | توضیح                                       |
| ------------------- | ------------------------------------------- |
| SQL Execution       | زمان اجرای Queryهای اصلی                    |
| Row Fetching        | زمان خواندن خروجی SQLite                    |
| Rust Processing     | زمان تجمیع و ساخت درخت حساب‌ها              |
| IPC Serialization   | زمان آماده‌سازی و انتقال اطلاعات به WebView |
| JS Data Preparation | زمان تبدیل پاسخ به ساختار نمایشی            |
| DOM Rendering       | زمان ساخت و نمایش جدول                      |
| Memory Usage        | بیشترین مصرف RAM                            |
| Disk I/O            | میزان خواندن و نوشتن دیسک                   |

همچنین زمان اجرای گزارش باید در پنج اجرای متوالی و در دو وضعیت دیتابیس گرم و سرد اندازه‌گیری شود.

این اندازه‌گیری مشخص می‌کند که واقعاً کدام قسمت باعث کندی است.

همچنین زمان Backup و Restore، میزان RAM و اندازه فایل نهایی در آزمون‌های حجیم ثبت شود.

### ۱۰-۲. صحت محاسبات گزارش‌های مالی

در مخزن شما فایل زیر وجود دارد:

`Docs/Accounting-Report-Signoff.md`

در آن وضعیت تأیید مستقل محاسبات گزارش‌های مالی همچنان `pending` است.

این موضوع را جدی می‌دانم.

آزمون مرجع نرم‌افزاری نشان می‌دهد که کد پس از تغییرات هنوز خروجی مورد انتظار قبلی را تولید می‌کند؛ اما این به‌تنهایی صحت طبقه‌بندی حساب‌ها و محاسبات را از نظر اصول حسابداری اثبات نمی‌کند.

پیشنهاد می‌کنم تراز آزمایشی، صورت سود و زیان و ترازنامه توسط یک حسابدار یا حسابرس مستقل، با محاسبات دستی و نمونه‌های واقعی ناشناس‌شده تأیید شوند.

به‌خصوص این موارد:

- جمع گردش حساب‌های کل و معین.
- جمع گردش تفصیلی و تأثیر آن در حساب معین.
- مانده افتتاحیه و اختتامیه.
- حساب‌های دارای ماهیت دوگانه.
- اسناد افتتاحیه و اختتامیه.
- اثر حساب‌های کاهنده درآمد.
- تراز بودن مجموع بدهکار و بستانکار در سطوح مختلف.

### ۱۰-۳. آزمون کامل برنامه با بک‌اند واقعی

در پروژه شما دو نوع آزمون وجود دارد:

1. آزمون رابط با Playwright که در آن بک‌اند Tauri با Mock شبیه‌سازی می‌شود.
2. آزمون‌های Rust که منطق واقعی بک‌اند و SQLite را بررسی می‌کنند.

این روش خوب است، اما هنوز یک پوشش کامل از تعامل واقعی WebView2 با بک‌اند SQLite در تمام فرم‌ها وجود ندارد.

پیشنهاد می‌کنم در مرحله بعد چند آزمون واقعی Windows/Tauri اضافه شود:

- باز کردن فرم تراز و تولید گزارش.
- تولید گزارش با دیتابیس حجیم.
- تغییر محدوده تاریخ و نوع گزارش.
- باز کردن دفتر کل از حساب انتخاب‌شده.
- جستجوی حساب.
- پیش‌نمایش چاپ تراز.
- بازیابی پایگاه داده در شرایطی که پنجره‌های گزارش باز هستند.

### ۱۰-۴. حفاظت شاخه اصلی GitHub

در مستند موجود، حفاظت شاخه اصلی به‌عنوان یک مورد مدیریتی نیازمند بررسی ذکر شده است.

پیشنهاد می‌کنم در GitHub برای شاخه `main` یک Ruleset تنظیم کنید تا:

- ادغام Pull Request بدون گذر موفق CI انجام نشود.
- آزمون‌های Rust و JavaScript الزامی باشند.
- آزمون‌های Playwright و Security Audit موفق باشند.
- Merge مستقیم محدود شود.
- برای تغییرات حساس حسابداری بازبینی کد اجباری باشد.

وضعیت واقعی این تنظیم از روی فایل‌های سورس قابل تأیید نیست و باید در تنظیمات مخزن کنترل شود.

### ۱۰-۵. بررسی دسترسی‌ها و امنیت رابط

در بررسی فایل‌های Tauri، تنظیمات امنیتی پایه مناسب بودند.

به‌خصوص فایل `src-tauri/capabilities/default.json` دسترسی پنجره‌ها را مشخص کرده و مجوزهای اضافی گسترده‌ای برای سیستم فایل یا اجرای فرمان‌های خارجی به همه پنجره‌ها نداده است.

همچنین در `tauri.conf.json` سیاست CSP تعریف شده است.

پیشنهاد تکمیلی من این است که در توسعه‌های بعدی، استفاده از Styleهای درون‌خطی نیز تا حد امکان کاهش یابد تا امکان محدودتر کردن سیاست `style-src` فراهم شود.

## ۱۱. یک نکته مهم درباره سرعت نسخه اجرایی

در بررسی فایل `run.bat` و `Cargo.toml` مشخص شد که تنظیمات کامپایل Release بهینه‌سازی بالایی دارند:

```
[profile.release]
codegen-units = 1
lto = true
opt-level = 3
```

اما دستور پیش‌فرض:

```
run.bat
```

برنامه را در حالت Debug می‌سازد.

این موضوع برای برنامه‌ای با عملیات محاسباتی زیاد اهمیت دارد.

بنابراین برای اندازه‌گیری واقعی سرعت، برنامه را با دستور زیر اجرا کنید:

```
run.bat release
```

یا نسخه نهایی را با:

```
build.bat portable
```

بسازید.

مقایسه سرعت Debug و Release را باید پیش از ارزیابی نتیجه بهینه‌سازی‌ها انجام داد.

# ۱۴. جمع‌بندی نهایی

# معماری پایه مناسب است

برنامه از نظر انتخاب Rust، SQLite و Tauri، ساختار نسبتاً مناسبی دارد. همچنین قسمت‌های مهمی مانند تراکنش ثبت سند، اعتبارسنجی حساب‌ها، حفاظت اسناد دائمی، Backup و گزارش‌های حسابداری با توجه به حجم پروژه طراحی شده‌اند.

با این حال، سه مسئله را مهم‌تر از بقیه می‌دانم:

اول: Query تراز آزمایشی.

مهم‌ترین مشکل عملکردی شناسایی‌شده، انجام تجمیع روی تمام ردیف‌های مرتبط قبل از اعمال محدودیت تاریخ پایان است. این موضوع می‌تواند زمان تولید گزارش را در دیتابیس‌های بزرگ افزایش دهد.

دوم: مدیریت اتصال SQLite.

نگهداری تمام عملیات پشت یک اتصال مشترک، مانع مناسبی برای افزایش هم‌زمانی برنامه نیست. معماری خواندن و نوشتن باید از یکدیگر تفکیک شود.

سوم: ورود اطلاعات حجیم.

در ورود ۳۰۰ هزار ردیف، بارگذاری و نگهداری اطلاعات در حافظه و اجرای دستورات تکراری SQL می‌تواند زمان و RAM زیادی مصرف کند.

یک نکته مهم دیگر: مشکل نمایش ندادن تراز را نمی‌توان تنها با بررسی GitHub به‌صورت قطعی به یک خط کد نسبت داد؛ برای تشخیص نهایی باید Query Plan و زمان اجرای واقعی روی دیتابیس شما بررسی شود. اما کد فعلی چند علت کاملاً قابل پیگیری برای این رفتار نشان می‌دهد.
