## ۱. خلاصه مدیریتی

بررسی ساختار مخزن، فایل‌های اصلی Rust، لایه SQLite، فرمان‌های Tauri، صفحات JavaScript، گزارش‌ها، آزمون‌ها، تنظیمات build و اجرای اخیر GitHub Actions نشان می‌دهد که **معماری فعلی برنامه برای ادامه توسعه مناسب است و بازنویسی کامل یا تغییر فناوری توصیه نمی‌شود.** ترکیب Tauri 2، Rust و SQLite برای یک نرم‌افزار حسابداری دسکتاپ انتخاب قابل دفاعی است؛ منطق حساس حسابداری عمدتاً در بک‌اند قرار گرفته و UI به‌عنوان لایه تعامل و نمایش عمل می‌کند.

با این حال، برنامه هنوز از نظر تأیید حرفه‌ای خروجی‌های حسابداری، آزمون عملیاتی واقعی در WebView2، تطبیق مستقل اختتامیه/افتتاحیه، بنچمارک حجم داده، و چند موضوع معماری و نگهداری نیازمند تکمیل است. بر اساس اجرای CI ثبت‌شده در بررسی اولیه، job مربوط به آخرین commit بررسی‌شده با شکست پایان یافته است؛ علت ثبت‌شده **خطای موقت HTTP 504 در دریافت فایل جانبی NSIS از GitHub** بوده، نه شکست کامپایل برنامه یا آزمون‌های Rust و JavaScript. در صحت‌سنجی این نوبت، API گیت‌هاب برای آن run پاسخ 404 داد؛ بنابراین وضعیت تازهٔ اجرا مستقلاً تأیید نشد.

### اولویت‌های فوری

۱. اجرای مجدد job ناموفق `desktop-build` و پایدارسازی دریافت dependency مربوط به NSIS.  
۲. تکمیل تأیید مستقل حسابدار/حسابرس برای پنج گزارش اصلی و چهار صورت تکمیلی؛ تا آن زمان خروجی رسمی نباید تأییدشده تلقی شود.  
۳. تثبیت سیاست تاریخچهٔ طبقه‌بندی برای پایگاه‌های داده‌ای که از نسخه‌های قبل از schema v13 ارتقا می‌یابند.  
۴. تکمیل سنجش baseline مصنوعی با دادهٔ واقعی/ناشناس‌شده و تعداد حساب‌های بیشتر؛ baseline مصنوعی ۱۰۰ و ۳۰۰ هزار ردیفی اکنون ثبت شده است.  
۵. افزودن آزمون واقعی چاپ/PDF در Windows WebView2، نه صرفاً تست مرورگر با mock.

## ۲. دامنه و روش بررسی

### ۲-۱. محدوده کد بررسی‌شده

ساختار recursive مخزن شامل ۱۸۳ فایل قابل مشاهده بود. بررسی روی مسیرهای اصلی زیر متمرکز شد:

- **پیکربندی و ساخت:** `package.json`، `package-lock.json`، `src-tauri/Cargo.toml`، `src-tauri/Cargo.lock`، `src-tauri/tauri.conf.json`، `build.bat`، `run.bat`.
- **فرمان‌های Tauri:** `src-tauri/src/commands/` شامل فرمان‌های حساب، سند، گزارش، چاپ، پایگاه داده و پنجره‌ها.
- **پایگاه داده و مهاجرت:** `src-tauri/src/db/` شامل `schema.rs`، `connection.rs`، `accounts.rs`، `classification.rs`، `fiscal_years.rs`، `closing.rs`، `backup.rs` و `audit.rs`.
- **چرخه سند:** `src-tauri/src/vouchers/` شامل `validation.rs`، `storage.rs`، `query.rs`، `import.rs`، `transfer.rs` و `bulk_delete.rs`.
- **گزارش‌ها:** `src-tauri/src/vouchers/reports/` شامل تراز آزمایشی، دفتر کل، دفتر روزنامه، صورت‌های مالی، صورت‌های تکمیلی و Integrity.
- **رابط کاربری:** صفحات `ui/js/pages/`، فایل‌های `ui/js/voucher/`، فرم‌های حساب و سند، منوها، CSS و صفحه چاپ.
- **آزمون و CI:** `tests/`، `tests/e2e/`، آزمون‌های Rust و `.github/workflows/ci.yml`.
- **مستندات موجود:** `README.md`، `Docs/Project-Status.md`، `Docs/Acc-Rust-Review-fa.md`، `Docs/Accounting-Report-Signoff.md` و `Docs/Data-Protection-and-Release-Policy.md`.

### ۲-۲. محدودیت‌های بررسی

بازبینی اولیه بر مبنای سورس و اطلاعات قابل مشاهده در GitHub انجام شد. در پیگیری محلی، آزمون‌های محدود parity در Rust و WebApp و benchmark مصنوعی Rust در build بهینه‌شده اجرا شدند؛ دیتابیس واقعی یا دادهٔ ناشناس‌شدهٔ کاربر استفاده نشد. وضعیت CI از اجرای واقعی GitHub Actions و log همان job استخراج شده است. بنابراین:

- یافته‌هایی که مستقیماً در سورس مشاهده شده‌اند به‌عنوان یافته کدنویسی مطرح شده‌اند.
- benchmark مصنوعی تنها baseline همین fixture و محیط اجرا را نشان می‌دهد و قابل تعمیم به دادهٔ واقعی یا تعداد حساب‌های بالاتر نیست؛ موارد کارایی همچنان «ریسک نیازمند اندازه‌گیری» هستند، نه باگ قطعی.
- صحت حرفه‌ای صورت‌های مالی فقط با تست نرم‌افزاری قابل اثبات نیست و به تأیید مستقل حسابدار/حسابرس نیاز دارد.
- وضعیت Branch Protection و Ruleset از تنظیمات مدیریتی GitHub به‌طور قطعی در این بررسی خوانده نشده است؛ باید در پنل مخزن بررسی شود.

## ۳. نقاط قوت فنی که باید حفظ شوند

این بخش برای ایجنت مهم است؛ اصلاحات نباید با حذف یا تضعیف کنترل‌های فعلی انجام شوند.

### ۳-۱. معماری لایه‌ای

ساختار کلی چنین است:

```text
HTML / CSS / JavaScript
        │ Tauri invoke
        ▼
Tauri Commands
        │
        ▼
Rust Domain / Application Logic
(accounts, vouchers, closing, reports, excel)
        │
        ▼
SQLite
(schema, triggers, transactions, indexes, backup)
```

منطق اعتبار حساب، تراز سند، اعتبار تاریخ، وضعیت سال مالی و دائمی‌سازی در بک‌اند کنترل می‌شود. این طراحی درست است. محاسبات مالی حساس را به JavaScript منتقل نکنید و به‌صرف مدرن‌سازی UI، فریم‌ورک یا معماری فعلی را بازنویسی نکنید.

### ۳-۲. مبلغ و محاسبات مالی

مبالغ در Rust به‌صورت عدد صحیح (`i64`) نگهداری می‌شوند و توابعی مانند `checked_add`، `checked_sub`، `checked_neg` و `checked_sum` برای جلوگیری از overflow در محاسبات وجود دارند. استفاده از `float` برای مبالغ حسابداری توصیه نمی‌شود.

### ۳-۳. اعتبارسنجی و ذخیره سند

در `src-tauri/src/vouchers/validation.rs` و `storage.rs` کنترل‌های زیر وجود دارند:

- تعداد و حداقل ردیف سند؛
- مبلغ صفر/منفی و ورود هم‌زمان بدهکار و بستانکار در یک ردیف؛
- تساوی جمع بدهکار و بستانکار؛
- صحت حساب پایه، تفصیلی ۱، رابطه والد/فرزند و هم‌گروه بودن؛
- فعال بودن حساب و سازگاری نوع سند؛
- معتبر بودن تاریخ و سال مالی باز؛
- کنترل شماره سند تکراری؛
- کنترل نسخه برای جلوگیری از overwrite تغییر هم‌زمان؛
- کلید idempotency برای جلوگیری از ثبت تکراری درخواست؛
- تراکنش SQLite و ثبت رویداد Audit Log.

### ۳-۴. محافظت از سند دائمی

در `schema.rs` triggerهایی برای جلوگیری از تغییر/حذف اسناد دائمی و ردیف‌های آن‌ها وجود دارد. مسیر برگشت بستن سال از allowlist کنترل‌شده و تراکنش اختصاصی استفاده می‌کند. این حفاظ‌ها نباید برای ساده‌کردن import یا اصلاح داده حذف شوند.

### ۳-۵. بهینه‌سازی موجود در گزارش تراز

در `src-tauri/src/vouchers/reports/trial_balance.rs` تجمیع گردش حساب‌ها در SQLite انجام می‌شود و خروجی تجمیعی با `HashMap` به ساختار حساب‌ها وصل می‌شود. این روش جایگزین الگویی شده که CTE تجمیعی را به‌ازای هر حساب دوباره اسکن می‌کرد و می‌توانست رفتار نزدیک به درجه‌دو ایجاد کند. محاسبه roll-up حساب‌های والد با memoization انجام می‌شود و جمع کل از بالاترین ردیف هر شاخه محاسبه می‌شود تا جمع والد و فرزند دوباره‌شماری نشود.

این مسیر باید حفظ و فقط بر اساس benchmark واقعی بهینه‌تر شود.

### ۳-۶. SQLite و دوام داده

در `db/connection.rs`، تنظیمات WAL، `foreign_keys=ON`، `busy_timeout=5000`، cache بزرگ‌تر، `temp_store=MEMORY`، `mmap_size` و `journal_size_limit` اعمال شده‌اند. `synchronous` عمداً روی مقدار امن FULL باقی مانده است تا سرعت نوشتن به قیمت ریسک از دست رفتن آخرین تراکنش‌های ثبت‌شده در قطع برق بهبود داده نشود.

### ۳-۷. تاریخچه طبقه‌بندی حساب و کنترل Integrity

در schema v13 جدول `account_classification_history` و انتخاب طبقه‌بندی معتبر در تاریخ گزارش اضافه شده است. پیش‌نمایش اثر تغییر گروه نیز وجود دارد. کنترل‌های Integrity مربوط به سند دائمی بدون سال مالی، تاریخ خارج از سال مالی و ردیف حل‌نشدهٔ سطح چهار اضافه شده‌اند.

### ۳-۸. Backup و امنیت پایه

پشتیبان قابل‌حمل `.hacc` با AES-256-GCM و مشتق‌سازی کلید مبتنی بر Argon2id رمزنگاری می‌شود. فایل قبل از بازیابی بررسی می‌شود و از دیتابیس فعال نسخه ایمنی گرفته می‌شود. این قابلیت ارزشمند است؛ با این حال رمزنگاری backup به‌معنای رمزنگاری فایل SQLite فعال نیست.

### ۳-۹. کنترل چاپ رسمی

در `src-tauri/src/commands/print.rs`، تابع `ensure_printable` برای صورت‌های مالی دارای Integrity به‌صورت سمت Rust اجرا می‌شود؛ گزارش رسمی با خطای Integrity چاپ نمی‌شود و گزارش کاری/موقت برای بررسی در دسترس می‌ماند. این کنترل نباید تنها به مخفی کردن دکمه در JavaScript تقلیل یابد.

## ۴. یافته‌های اولویت بحرانی و بالا (P1)

### P1-01 ـ شکست آخرین CI در مرحله بسته‌بندی NSIS

**اولویت فوری**

**شدت:** بالا برای ادغام و انتشار؛ پایین از نظر ریسک داده  
**وضعیت:** تأییدشده در GitHub Actions  
**مسیر اصلی:** `.github/workflows/ci.yml`، job `desktop-build`، مرحله `Bundle Windows installer (without binary patching)`

**شاهد:** آخرین اجرای CI روی commit `e03b92a...` چهار job داشته است. سه job اول موفق بوده‌اند. ساخت EXE، build دیباگ و smoke test واقعی Tauri/WebView2 موفق شده‌اند. مرحله bundle هنگام دریافت `nsis_tauri_utils.dll` با HTTP 504 متوقف شده است.

**وضعیت صحت‌سنجی این نوبت:** اطلاعات اجرای یادشده از طریق GitHub API اکنون قابل بازیابی نبود (404). بنابراین این شرح صرفاً شاهد ثبت‌شده در بررسی اولیه است و وضعیت فعلی یا رفع مشکل را تأیید نمی‌کند.

**ریسک:** CI روی شاخه اصلی قرمز می‌ماند و jobهای وابسته، تولید artifact و تأیید release انجام نمی‌شود. retry دستی ممکن است مشکل را موقتاً رفع کند، اما پایداری تکرارپذیر build همچنان تضمین نشده است.

**راهکار پیشنهادی:**

۱. ابتدا فقط job ناموفق `desktop-build` را یک بار مجدداً اجرا کنید؛ کل jobهای موفق را بی‌دلیل تکرار نکنید.  
۲. در workflow، دریافت ابزارهای جانبی NSIS را به‌صورت صریح و با retry محدود و backoff انجام دهید؛ مثلاً سه تلاش با فاصله افزایشی.  
۳. اگر ابزار پیش‌دانلود می‌شود، SHA-256 یا hash مورد انتظار آن را با مقدار upstream/Tauri تطبیق دهید؛ اعتبارسنجی hash را حذف یا غیرفعال نکنید.  
۴. در صورت پشتیبانی رسمی و قابل نگهداری، NSIS و `nsis-tauri-utils` را در cache کنترل‌شدهٔ CI نگهداری کنید. Cache باید کلید نسخه‌دار داشته باشد و با تغییر نسخه Tauri یا NSIS باطل شود.  
۵. خطای HTTP 5xx را از خطاهای واقعی bundle تفکیک کنید. اگر retryها تمام شد، job باید با پیام روشن شکست بخورد.  
۶. پس از اصلاح، اجرای کامل CI روی همان commit یا commit اصلاحی را بررسی کنید.

**معیار پذیرش:**

- `verify`، `ui-e2e`، `security-audit` و `desktop-build` همگی موفق باشند.
- EXE و installer ساخته شوند و artifact شامل `release-metadata.json` و `SHA256SUMS.txt` باشد.
- در صورت نبود secret امضا، خروجی فقط به‌عنوان build داخلی unsigned برچسب بخورد؛ release رسمی همچنان امضای معتبر و sign-off نیاز داشته باشد.
- هیچ `skip hash validation` یا دریافت غیرقابل‌اعتبارسنجی به راه‌حل اضافه نشود.

### P1-02 ـ تأیید مستقل حسابداری صورت‌های مالی هنوز انجام نشده است

**شدت:** بسیار بالا برای استفاده رسمی  
**وضعیت:** باز؛ اقدام انسانی است و با تغییر کد به‌تنهایی بسته نمی‌شود.  
**مسیرها:** `Docs/Accounting-Report-Signoff.md`، `src-tauri/src/vouchers/reports/financial_statements.rs`، `src-tauri/src/vouchers/reports/supplementary_statements.rs`، `src-tauri/src/vouchers/reports/fixtures/`

**شرح:** وجود تست مرجع یا درست اجرا شدن تابع محاسباتی، صحت حرفه‌ای طبقه‌بندی و ارائه صورت مالی را ثابت نمی‌کند. fixture موجود، تراز آزمایشی، صورت سود و زیان و ترازنامه را pin می‌کند؛ چهار صورت تکمیلی در این fixture مرجع مستقل ندارند و عمدتاً با آزمون‌های محاسباتی/چاپ داخل پروژه پوشش داده شده‌اند.

**ریسک:** ممکن است نرم‌افزار یک خروجی ثابت و تکرارپذیر تولید کند، اما قواعد طبقه‌بندی حساب، ماهیت، حساب کاهنده، مبنای جریان نقد، تخصیص سود یا بهای تمام‌شده با سیاست حسابداری شرکت یا استاندارد قابل اعمال هم‌خوان نباشد.

**راهکار پیشنهادی:**

۱. برای هر پنج گزارش اصلی و چهار صورت تکمیلی یک سناریوی مرجع قابل محاسبه تهیه شود.  
۲. نمونه داده باید شامل حساب‌های بدهکار/بستانکار، دوماهه یا چنددوره‌ای، حساب کاهنده، افتتاحیه، اختتامیه، حساب موقت، تفصیلی ۱ و حساب طبقه‌بندی‌نشده باشد.  
۳. خروجی Rust با محاسبه مستقل در Excel یا محاسبه دستی در سه سطح تطبیق داده شود: ردیف/حساب، جمع سرفصل و جمع نهایی.  
۴. برای هر گزارش فرمول، مبنای دوره، حساب‌های مشمول، موارد استثنا و روش برخورد با مانده منفی مستند شود.  
۵. صورت بهای تمام‌شده تا زمانی که ماژول موجودی و تولید وجود ندارد، دامنه محدود خود را صریح اعلام کند؛ از معرفی آن به‌عنوان محاسبه جامع بهای تمام‌شده تولید خودداری شود.  
۶. حسابدار/حسابرس مستقل نام، تاریخ، مبنای بررسی و SHA-256 fixture را در `Accounting-Report-Signoff.md` ثبت کند.  
۷. تغییر محاسبات یا fixture باید sign-off قبلی را برای بازبینی مجدد بی‌اعتبار کند؛ ایجنت نباید status را خودکار `approved` کند.

**معیار پذیرش:** sign-off معتبر با نام و تاریخ واقعی ثبت شود؛ hash فایل مرجع با فایل جاری منطبق باشد؛ اختلاف محاسباتی حل‌نشده وجود نداشته باشد؛ گیت انتشار رسمی فقط پس از این اقدام انسانی مجاز شود.

### P1-03 ـ تاریخچه طبقه‌بندی پیش از ارتقا به schema v13 قابل بازسازی نیست

**شدت:** بالا برای بازتولید گزارش‌های سنواتی  
**وضعیت:** قابلیت نسخه‌بندی آینده‌نگر پیاده‌سازی شده؛ محدودیت داده تاریخی باقی است.  
**مسیرها:** `src-tauri/src/db/classification.rs`، `src-tauri/src/db/schema.rs`، `src-tauri/src/db/accounts.rs`، `Docs/Project-Status.md`

**شرح:** در migration نسخه ۱۳ برای حساب‌های موجود snapshot پایه با `valid_from = 0001/01/01` ساخته می‌شود. این snapshot وضعیت فعلی حساب در زمان ارتقا را ثبت می‌کند؛ تاریخچه واقعی تغییرات سال‌های قبل را از نو ایجاد نمی‌کند. تغییرهای جدید از تاریخ روز ثبت می‌شوند و گزارش‌های بعدی می‌توانند طبقه‌بندی معتبر در تاریخ را بخوانند.

**ریسک:** اگر حسابی در سال ۱۴۰۴ طبقه‌بندی متفاوتی داشته و قبل از v13 تغییر داده شده باشد، snapshot پایه وضعیت زمان ارتقا را برای تمام تاریخ‌های پیش از آن بازمی‌گرداند. بنابراین گزارش قدیمی قابل بازتولید بر اساس «اطلاعات موجود زمان ارتقا» است، نه لزوماً نسخه‌ای که هنگام صدور گزارش در سال‌های گذشته وجود داشته است.

**راهکار پیشنهادی:**

۱. در راهنمای ارتقا، صریحاً توضیح داده شود که snapshot پایه تاریخچه واقعی قبل از v13 نیست.  
۲. پیش از ارتقا از دیتابیس نسخه‌دار backup گرفته شود و hash و نسخه schema در manifest نگهداری شود.  
۳. برای مشتریانی که فایل‌های گزارش یا backup قدیمی دارند، امکان واردکردن snapshotهای معتبر تاریخی به‌صورت ابزار مدیریتی جداگانه بررسی شود؛ حدس زدن تاریخچه یا ساخت خودکار آن از Audit Log ناقص ممنوع است.  
۴. سیاست اصلاح طبقه‌بندی در دوره بسته باید روشن شود: تغییر صرفاً از امروز یا اصلاح با تاریخ مؤثر گذشته همراه با دلیل، تأیید سطح بالا و ثبت snapshot قبل/بعد.  
۵. اگر گردش‌کار backdating هنوز وجود ندارد، UI نباید وانمود کند که امکان اصلاح تاریخ گذشته را فراهم می‌کند.

**معیار پذیرش:** تست migration از نسخه‌های قدیمی با دیتابیس کپی‌شده؛ گزارش‌های قبل/بعد migration با محدوده و محدودیت روشن مقایسه شوند؛ اسناد قدیمی حذف یا بازطبقه‌بندی پنهانی نشوند؛ سیاست اصلاح دوره گذشته در مستندات محصول ثبت شود.

### P1-04 ـ وضعیت Branch Protection و اجرای CI روی commit نهایی باید قطعی شود

**شدت:** بالا برای کنترل انتشار  
**وضعیت:** نیازمند تأیید تنظیمات GitHub  
**مسیرها:** `.github/workflows/ci.yml`، `scripts/check-report-signoff.mjs`، `Docs/Data-Protection-and-Release-Policy.md`

**شرح:** workflow گیت‌های لازم برای build و audit را تعریف کرده و release رسمی را به signing secrets و sign-off مالی وابسته می‌کند. اما وجود workflow به‌تنهایی اثبات نمی‌کند که branch protection یا ruleset شاخه `main` الزام اجرای موفق این jobها را اعمال کرده است.

**راهکار پیشنهادی:**

- برای `main` الزام Pull Request و حداقل یک review مستقل در تغییرات مدل حساب، migration، سند، بستن سال و گزارش مالی فعال شود.
- jobهای ضروری `verify`، `ui-e2e`، `security-audit` و `desktop-build` در ruleset مشخص شوند؛ سیاست شکست موقت dependency نیز شفاف باشد.
- force push و حذف branch اصلی محدود شوند.
- release رسمی از build داخلی unsigned جدا باشد و فقط پس از sign-off، CI موفق و امضای معتبر اجرا شود.
- مقدار واقعی Branch Protection در مستند release ثبت شود؛ از روی سورس حدس زده نشود.

**معیار پذیرش:** یک PR آزمایشی نتواند بدون عبور از checkهای الزامی وارد `main` شود؛ release رسمی در وضعیت pending sign-off شکست بخورد؛ پس از موفقیت کامل، metadata و امضا قابل بررسی باشد.

## ۵. منطق حسابداری و گزارش‌ها (P2 با اثر مالی بالا)

### P2-01 ـ تکمیل تطبیق بین‌گزارشی (Trial Balance / Ledger / Statements)

**شدت:** بالا  
**وضعیت:** بخشی از Integrity و آزمون parity محدود Rust/WebApp وجود دارد؛ گزارش تطبیق واحد و پوشش کامل موارد زیر هنوز باقی است.  
**مسیرها:** `src-tauri/src/vouchers/reports/integrity.rs`، `trial_balance.rs`، `ledger.rs`، `financial_statements.rs`، `supplementary_statements.rs`

**شرح:** Integrity کنترل‌های مهمی نظیر حساب طبقه‌بندی‌نشده، حساب کاهنده نامعتبر، تراز بودن ترازنامه، مانده حساب موقت، سند بستن و ارتباط سند با سال مالی را پوشش می‌دهد. سه کنترل اخیر مربوط به سند بدون سال مالی، تاریخ خارج از سال مالی و ردیف سطح چهار نیز اضافه شده‌اند. با این حال، گزارش تطبیق جامع که نشان دهد جمع‌های دفتر کل، تراز آزمایشی و صورت‌های مالی از یک مبنای داده و طبقه‌بندی استفاده می‌کنند، هنوز نیازمند تکمیل است.

**اقدامات:**

۱. کنترل جمع بدهکار/بستانکار در سطح سند، سطح حساب پایه، معین، تفصیلی ۱ و کل را مستقل تعریف کنید.  
۲. برای هر سطح، جمع ردیف‌های فرزند باید با جمع والد برابر باشد؛ مراقب double counting در خروجی‌های چندسطحی باشید.  
۳. مانده دفتر کل و تراز آزمایشی باید برای حساب و بازه مشابه برابر باشد.  
۴. مجموع طبقه‌بندی‌شده و طبقه‌بندی‌نشده در صورت‌های مالی با گردش حساب‌های منبع تطبیق داده شود.  
۵. کنترل‌های افتتاحیه/اختتامیه، حساب کاهنده، split-by-sign، dual nature و حساب‌های بدون تفصیلی در fixture پوشش داده شوند.  
۶. خطاها severity، شناسه پایدار، حساب/سند مرتبط و اقدام پیشنهادی داشته باشند.

**معیار پذیرش:** تست مثبت و منفی برای اختلاف عمدی در هر سطح؛ عدم چاپ رسمی در وجود خطای مسدودکننده؛ گزارش کاری باید خطا را قابل مشاهده و قابل drill-down کند.

**پیگیری جاری:** آزمون رگرسیون محدود در هر دو برنامه اکنون سناریوی مشترک افتتاحیه، فروش و هزینه را برای جمع‌های تراز آزمایشی، سود و زیان و ترازنامه کنترل می‌کند. این آزمون، تطبیق Ledger، تفصیلی‌ها، اختلاف‌های عمدی، اختتامیه/افتتاحیهٔ چندساله و همه صورت‌های تکمیلی را پوشش نمی‌دهد؛ بنابراین وضعیت این مورد فقط «بخشی انجام شد» است و معیار پذیرش بالا هنوز برآورده نشده است.

### P2-02 ـ افزودن گزارش مستقل تطبیق انتقال مانده بین دو سال مالی

**شدت:** بالا  
**وضعیت:** پیش‌شرط‌های زیادی در مسیر closing وجود دارد؛ گزارش reconciliation مستقل لازم است.  
**مسیر:** `src-tauri/src/db/closing.rs`، `src-tauri/src/db/fiscal_years.rs`

**شرح:** مسیر closing پیش از انتقال، وضعیت سال‌ها، سند اختتامیه، سند افتتاحیه قبلی، مانده حساب موقت، تراز سند و برخی ناسازگاری‌ها را کنترل می‌کند و انتقال در تراکنش انجام می‌شود. اما کاربر/حسابرس به یک گزارش مستقل نیاز دارد که نتیجه انتقال را بعد از اجرا نیز قابل بررسی کند.

**راهکار:**

گزارش `Carry Forward Reconciliation` با ستون‌های زیر ایجاد شود:

- کد و عنوان حساب؛
- کد و عنوان تفصیلی ۱ (در صورت وجود)؛
- مانده پایان سال قبل به تفکیک بدهکار/بستانکار؛
- مانده افتتاحیه سال بعد به تفکیک بدهکار/بستانکار؛
- اختلاف ریالی؛
- وضعیت تطبیق و توضیح علت اختلاف.

گزارش باید حساب‌های کاهنده و مانده‌های دوطرفه را با منطق signed balance مدیریت کند. حساب‌های موقت نباید به افتتاحیه سال بعد منتقل شوند مگر سیاست صریح و مجاز وجود داشته باشد. حساب‌های فاقد تفصیلی نیز نباید حذف شوند.

**معیار پذیرش:** دو سال مالی متوالی با حساب‌های متعدد، حساب کاهنده، تفصیلی ۱، مانده صفر و مانده دوطرفه؛ اختلاف عمدی در یک account باید دقیقاً همان حساب را علامت‌گذاری کند؛ اجرای مجدد انتقال نباید سند افتتاحیه تکراری بسازد.

### P2-03 ـ پوشش مستقل و مرجع چهار صورت تکمیلی

**شدت:** بالا برای استفاده رسمی  
**مسیر:** `src-tauri/src/vouchers/reports/supplementary_statements.rs` و چهار صفحه UI مربوط

صورت‌های جریان وجوه نقد، تغییرات حقوق مالکانه، بهای تمام‌شده و تخصیص سود پیاده‌سازی شده‌اند و به UI متصل‌اند. مسئله باقی‌مانده، تأیید قواعد و دامنه خروجی است.

**راهکار:**

- برای جریان وجوه نقد، روش غیرمستقیم، تفکیک عملیات/سرمایه‌گذاری/تأمین مالی و تطبیق افزایش/کاهش وجه نقد با تغییر موجودی اول و آخر دوره مستند شود.
- برای تغییرات حقوق مالکانه، آورده، برداشت/تقسیم سود، سود دوره و اصلاحات سنواتی به‌صورت جداگانه تست شوند.
- برای تخصیص سود، سود قابل تخصیص، اندوخته‌ها، سود سهام و مانده انتقالی کنترل شود.
- برای بهای تمام‌شده، تا زمانی که ماژول موجودی/تولید و جریان مواد/کالا وجود ندارد، دامنه گزارش محدود و آشکار باشد.

### P2-08 ـ جلوگیری از قفل طولانی اتصال مشترک SQLite

**شدت:** متوسط، وابسته به concurrent workload  
**مسیر:** `src-tauri/src/db/connection.rs`

**شاهد کد:** `Database::with_conn` یک `Mutex<Connection>` را قفل می‌کند و تمام عملیات SQL از همان اتصال عبور می‌کنند. این روش برای تراکنش‌های یک‌نویسنده‌ای ساده و قابل کنترل است، اما گزارش سنگین می‌تواند خواندن/نوشتن سایر پنجره‌ها را پشت mutex منتظر نگه دارد.

**راهکار پیشنهادی با احتیاط:**

۱. زمان انتظار برای گرفتن mutex، مدت اجرای query و مدت تراکنش به تفکیک command ثبت شود.  
۲. سناریوی اجرای هم‌زمان تراز آزمایشی، ذخیره سند، فهرست اسناد و backup تست شود.  
۳. اگر contention واقعی مشاهده نشد، معماری فعلی حفظ شود. صرفاً برای «مدرن‌تر شدن» pool اضافه نکنید.  
۴. اگر مسئله تأیید شد، یک pool محدود read-only یا حداقل اتصال مجزا برای گزارش‌ها بررسی شود؛ نوشتن همچنان در یک مسیر کنترل‌شده باقی بماند.  
۵. هر read connection باید تنظیمات `foreign_keys`/`busy_timeout` و snapshot consistency مناسب داشته باشد.  
۶. restore، backup، migration و تعویض فایل باید lifecycle واضح برای توقف و بازسازی همه connectionها داشته باشند.  
۷. اجرای SQL همگام در فرمان‌های async باید از نظر thread و زمان blocking بررسی شود؛ در صورت نیاز، queryهای طولانی به worker مناسب منتقل شوند.

**معیار پذیرش:** آزمون هم‌زمانی با backup/restore و report؛ عدم قفل یا از دست رفتن داده؛ زمان انتظار ذخیره سند هنگام اجرای گزارش بهبود قابل اندازه‌گیری داشته باشد.

### P2-09 ـ بهبود جست‌وجوی متن و صفحه‌بندی داده‌های طولانی

**شدت:** متوسط  
**مسیرها:** `src-tauri/src/vouchers/query.rs`، `src-tauri/src/vouchers/reports/journal.rs`، `ledger.rs`

**شاهد کد:** جست‌وجو با الگوی `LIKE '%term%'` در شماره، شرح، نوع، نام حساب، کد حساب، نام تفصیلی و شرح ردیف انجام می‌شود. شرط `EXISTS` نیز ردیف‌های سند و حساب‌ها را برای هر سند جست‌وجوشده بررسی می‌کند. صفحه‌بندی فعلی از `LIMIT/OFFSET` استفاده می‌کند. نرمال‌سازی رقم فارسی/عربی و «ی/ي» و «ک/ك» از قبل وجود دارد و باید حفظ شود.

**ریسک:** wildcard ابتدایی معمولاً باعث می‌شود B-tree index برای lookup متن معمولی به‌خوبی استفاده نشود. صفحات با offset بالا نیز می‌توانند هزینه اسکن/ردکردن ردیف زیادی ایجاد کنند. هزینه اصلی باید با query plan واقعی اثبات شود.

**راهکار:**

۱. برای queryهای پرتکرار `EXPLAIN QUERY PLAN` و زمان اجرای ۱۰۰k/۳۰۰k ردیف را ثبت کنید.  
۲. برای فیلدهای جست‌وجو، ستون نرمال‌شده یا FTS5 را ارزیابی کنید؛ پشتیبانی و رفتار tokenizer با فارسی، ارقام، نیم‌فاصله، «ی/ي» و «ک/ك» باید تست شود.

## ۹. امنیت و حفاظت داده

### P2-15 ـ تعیین سیاست حفاظت فایل دیتابیس فعال در حالت سکون

**شدت:** متوسط تا بالا بر اساس محیط استقرار

**وضعیت صحت‌سنجی:** تأیید شد؛ برنامه SQLite عادی را باز می‌کند و رمزنگاری `.hacc` به معنی رمزنگاری فایل فعال نیست. مستند سیاست حفاظت داده به‌روزرسانی شد تا این محدودیت و کنترل‌های پیشنهادی استقرار را صریح کند. رمزنگاری سطح فایل برای دیتابیس فعال همچنان پیاده‌سازی نشده است.

فایل دیتابیس عملیاتی با SQLite عادی باز می‌شود. backup قابل حمل `.hacc` رمزنگاری شده است؛ اما فایل اصلی دیتابیس، WAL، SHM و فایل‌های موقت در سطح SQLite رمزنگاری‌شده نیستند.

**راهکار:**

- در نصب Windows، ACL پوشه AppData به حساب Windows کاربر محدود و در مستند نصب تشریح شود.
- BitLocker برای دیسک میزبان داده در محیط‌های مناسب توصیه/الزام شود.
- محل backup، export، PDF، فایل Excel و فایل‌های موقت نیز در سیاست داده پوشش داده شوند.
- SQLCipher فقط در صورتی ارزیابی شود که الزامات امنیتی واقعی نیازمند رمزنگاری در سطح فایل باشند؛ هزینه migration، پشتیبانی، بازیابی، backup و compatibility بررسی شود.
- cleanup فایل موقت پس از crash تست شود؛ حذف فایل temp نباید backup معتبر یا تنها نسخه داده را از بین ببرد.

**معیار پذیرش:** راهنمای حفاظت داده و backup/restore روی دستگاه دوم؛ تست ACL؛ بازیابی `.hacc` با رمز درست/غلط؛ آزمون crash هنگام backup/restore.

## ۱۲. دستورالعمل‌های اجباری برای ایجنت برنامه‌نویسی

این قسمت را می‌توان مستقیماً به‌عنوان دستورکار ایجنت VS Code استفاده کرد.

### ۱۲-۱. قبل از تغییر کد

۱. ابتدا branch و commit فعلی را ثبت کنید و مطمئن شوید working tree کاربر تغییرات محلی مهم ندارد.  
۲. کد و تست‌های همان مسیر را کامل بخوانید؛ به خلاصه گزارش اکتفا نکنید.  
۳. هر یافته را به یکی از این دسته‌ها نسبت دهید: باگ قطعی، ریسک امنیتی، محدودیت معماری، بدهی فنی، یا فرضیه نیازمند benchmark.  
۴. برای هر تغییر، دامنه فایل‌ها و تست رگرسیون لازم را قبل از ویرایش بنویسید.

### ۱۲-۲. قواعد مالی غیرقابل مذاکره

- منطق مبلغ پولی را به float تبدیل نکنید.
- کنترل تراز سند، سال مالی، وضعیت دائمی، اعتبار حساب و رابطه تفصیلی را فقط در UI انجام ندهید؛ کنترل Rust و DB باید باقی بماند.
- برای «سبز شدن تست» expected valueهای fixture را بدون بررسی حسابداری تغییر ندهید.
- گزارش‌های رسمی را با حذف Integrity gate یا تبدیل خطا به warning قابل چاپ نکنید.
- حساب طبقه‌بندی‌نشده را به‌طور خودکار داخل سرفصل دلخواه قرار ندهید.
- در migration، سند یا ردیف قدیمی را حذف یا بازنویسی خاموش نکنید.
- وضعیت sign-off را ایجنت به `approved` تغییر ندهد؛ این تأیید فقط توسط حسابدار/حسابرس مجاز انجام می‌شود.
- تراکنش و idempotency مسیر import و save حفظ شود.
- اصلاح تاریخچه طبقه‌بندی باید مطابق سیاست تاریخ مؤثر باشد و هرگز تاریخ گذشته را بدون مجوز بازنویسی نکند.

### ۱۲-۳. قواعد کارایی

- ابتدا پروفایل و benchmark بگیرید، سپس optimization کنید.
- برای هر تغییر SQL، query plan و زمان قبل/بعد ثبت شود.
- برای هر تغییر UI، تعداد DOM node و زمان رندر را اندازه بگیرید.
- connection pool یا cache پیچیده را بدون اثبات bottleneck اضافه نکنید.
- totalهای گزارش باید بر کل dataset فیلترشده محاسبه شوند، نه صفحه یا ردیف‌های virtualized.
- نتایج گزارش قبل و بعد از optimization باید از نظر عددی برابر باشند.

### ۱۲-۴. قواعد تحویل هر فاز

برای هر فاز یک commit یا patch محدود تحویل شود و همراه آن این موارد ارائه شوند:

۱. فهرست فایل‌های تغییرکرده؛  
۲. خلاصه تغییر و علت فنی؛  
۳. تست‌های اجراشده و نتیجه دقیق؛  
۴. اگر تستی اجرا نشده، دلیل؛  
۵. خروجی benchmark قبل/بعد در اصلاحات کارایی؛  
۶. ریسک باقی‌مانده و روش rollback؛  
۷. دستورهای دقیق build و test برای کاربر.

## ۱۳. چک‌لیست آزمون نهایی

### ۱۳-۱. JavaScript و UI

```powershell
npm ci
npm run check:js
npm run lint:js
npm test
npx playwright install chromium
npm run test:e2e
npm run check:signoff
```

نکته: تا وقتی تأیید مستقل حسابدار/حسابرس در وضعیت `pending` است، اجرای `npm run check:signoff` ممکن است مطابق طراحی ناموفق باشد؛ این رفتار گیت انتشار است، نه شکست تست محاسبات. برای سبز کردن آن نباید وضعیت sign-off را به‌صورت دستی یا خودکار جعل کرد.

### ۱۳-۲. Rust

```powershell
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --all-features -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml
```

اگر افزودن `-D warnings` در CI هنوز در سیاست فعلی تأیید نشده است، ابتدا تغییر را در branch جدا اجرا کنید و سپس workflow و مستندات را هم‌راستا کنید.

### ۱۳-۳. Windows و Tauri

```powershell
cargo build --manifest-path src-tauri/Cargo.toml
npm run test:smoke:windows
npm run build
```

در runner ویندوز، علاوه بر این‌ها، ساخت installer NSIS، امضای EXE و installer در release رسمی، `signtool verify` و استخراج hash باید بررسی شوند.

### ۱۳-۴. داده و حسابداری

- ثبت سند متوازن و رد سند نامتوازن؛
- رد حساب غیرفعال و تفصیلی متعلق به معین دیگر؛
- بازاعتبارسنجی زمان دائمی‌سازی؛
- عدم تغییر اسناد دائمی از مسیر عادی؛
- کنترل شماره سند تکراری و idempotency؛
- تاریخ شمسی، کبیسه و مرز سال مالی؛
- تغییر طبقه‌بندی پس از v13 و ثبات گزارش گذشته؛
- گزارش حساب کاهنده، dual nature و UNCLASSIFIED؛
- بستن، برگشت بستن و انتقال مانده؛
- تطبیق اختتامیه/افتتاحیه؛
- import Excel خراب/حجیم/cancel و rollback؛
- backup عادی و `.hacc`، رمز صحیح/غلط و بازیابی روی دستگاه دیگر؛
- چاپ/PDF واقعی در WebView2.

## ۱۵. نتیجه نهایی

Acc-Rust از نظر ساختار پایه، تفکیک UI و منطق Rust، کنترل‌های ثبت سند، schema و مهاجرت، backup و چارچوب گزارش‌گیری بنیان مناسبی دارد. در بررسی فعلی موردی مشاهده نشد که بازنویسی کامل برنامه یا کنار گذاشتن Tauri/Rust/SQLite را توجیه کند.

در مقابل، **آمادگی برای استفاده رسمی حسابداری هنوز به‌صورت کامل تأیید نشده است**. بزرگ‌ترین ریسک‌ها عبارت‌اند از: نبود sign-off مستقل، محدودیت تاریخچه طبقه‌بندی قبل از v13، نبود reconciliation مستقل بین دو سال مالی، نبود تست چاپ واقعی WebView2 و نیاز به سنجش baseline روی دادهٔ واقعی/ناشناس‌شده؛ benchmark مصنوعی ۱۰۰هزار و ۳۰۰هزار ردیفی و تطبیق محدود Rust/WebApp انجام شده‌اند، اما جایگزین این موارد نیستند. بر اساس شاهد اجرای ثبت‌شده در گزارش اولیه، CI به دلیل timeout سرویس دانلود NSIS قرمز بوده است؛ اجرای تازه در این نوبت قابل بررسی نبود و باید در GitHub پیگیری شود.

پیشنهاد نهایی این است که ایجنت ابتدا فاز صفر را تکمیل کند، سپس به‌ترتیب سراغ تأیید خروجی‌های مالی، reconciliation، benchmark و بهینه‌سازی مبتنی بر اندازه‌گیری برود. refactor فایل‌های بزرگ و تغییر معماری اتصال SQLite باید پس از ثبت رفتار فعلی و فقط در patchهای کوچک انجام شود.

**اصل راهنما برای تمام اصلاحات:** هیچ بهینه‌سازی یا refactor نباید موجب تغییر خاموش در ارقام، طبقه‌بندی حساب‌ها، دامنه گزارش، وضعیت اسناد دائمی یا مانده انتقالی شود. صحت مالی بر سرعت و زیبایی کد مقدم است؛ سرعت نیز باید با benchmark اثبات شود، نه با حدس.
