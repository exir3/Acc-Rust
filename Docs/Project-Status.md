# وضعیت پروژه Acc-Rust

**آخرین به‌روزرسانی:** ۸ نوامبر ۲۰۲۶<br>
**مبنای بررسی:** شاخه `main`، commit `94da09a16c3cd41310f159be42d080ed2dcaf4e0` و تغییرات جاری رابط کاربری/آزمون‌ها<br>
**مرجع تفصیلی:** [گزارش جامع بررسی فنی و حسابداری](Acc-Rust-Review-fa.md)<br>
**وضعیت انتشار:** «نیازمند تأیید»؛ تا امضای حسابدار/حسابرس مستقل و اجرای موفق CI روی commit نهایی، خروجی رسمی صورت‌های مالی قطعی نیست.

> این سند تنها مرجع خلاصهٔ وضعیت پروژه است. جزئیات یافته‌ها، شواهد کد و معیارهای پذیرش در
> [گزارش جامع بررسی فنی و حسابداری](Acc-Rust-Review-fa.md) نگهداری می‌شود. گزارش‌های فنی
> قدیمی‌تر فقط به‌عنوان تاریخچه در پوشهٔ `Docs/Archive/` باقی مانده‌اند و مرجع وضعیت فعلی نیستند.

## ۱. خلاصهٔ اجرایی

Acc-Rust از نظر زیرساخت یک نرم‌افزار حسابداری دسکتاپ، پایهٔ مناسبی دارد: مدل حساب
چهارسطحی، اعتبارسنجی سند، کنترل سال مالی، بستن و انتقال مانده، تراکنش‌های SQLite،
پشتیبان‌گیری رمزنگاری‌شده و ثبت رویدادها پیاده‌سازی شده‌اند. معماری فعلی Tauri +
Rust + SQLite برای ادامهٔ کار مناسب است و بازنویسی کامل توجیه ندارد.

**موارد مهم انجام‌شده:**

- پنج گزارش اصلی (دفتر روزنامه، دفتر کل، تراز آزمایشی، صورت سود و زیان و ترازنامه)
  و چهار صورت تکمیلی (جریان وجوه نقد، تغییرات حقوق مالکانه، بهای تمام‌شده و
  تخصیص سود) در Rust، UI و چاپ وجود دارند.
- اتصال رابط کاربری چهار صورت تکمیلی در بازبینی ۸ نوامبر ۲۰۲۶ اصلاح شد؛ پیش از آن
  فایل‌های صفحه بارگذاری نمی‌شدند و گزینه‌های منو به صفحهٔ مربوط لینک نبودند.
- اعتبارسنجی ماهیت حساب کاهنده، گیت Integrity چاپ رسمی، حذف سند افتتاحیه از سود
  دوره، بازاعتبارسنجی سند هنگام دائمی‌سازی و کنترل مانده‌های طبقه‌بندی‌نشده
  پیاده‌سازی شده‌اند.
- آزمون رگرسیون اتصال UI چهار صورت به مجموعهٔ آزمون‌های فرانت‌اند اضافه شد.

**موارد باز مهم:**

- طبقه‌بندی حساب‌ها تاریخ اعتبار/نسخه‌بندی مؤثر ندارد؛ تغییر امروز می‌تواند
  بازتولید گزارش تاریخی را تغییر دهد.
- تأیید مستقل حسابدار/حسابرس برای ارقام و طبقه‌بندی صورت‌های مالی انجام نشده است.
- تطبیق عددی کامل خروجی گزارش‌ها با WebApp و محاسبهٔ دستی مستقل انجام نشده است؛
  فقط وجود مسیرها و منطق‌های متناظر بررسی شده است.
- وضعیت Branch Protection و اجرای CI روی commit جاری در این محیط بررسی نشده است.
- کارایی در حجم بالا با benchmark واقعی و دادهٔ ۳۰۰ هزار ردیفی تأیید نشده است.
- آزمون کامل UI → IPC → SQLite و چاپ/PDF واقعی در WebView2 وجود ندارد.

(P1-01، P1-03 از نظر پیاده‌سازی و اتصال UI، P1-05، P2-01، P2-04 و P2-06) در
جدول نیامده‌اند؛ تأیید صحت حسابداری صورت‌های تکمیلی زیر P1-04 باقی است.

### بک‌لاگ تکمیلی

- آزمون‌های منفی Excel: فایل خراب، ZIP bomb، ابعاد غیرعادی و سلول‌های merged.
- آزمون هم‌زمانی چند پنجرهٔ واقعی و رفتار قفل/به‌روزرسانی.
- بازیابی backup عادی و `.hacc` روی دستگاه دوم و بررسی ACL.
- آزمون‌های property-based برای مرزهای مبلغ، تعداد ردیف و تاریخ.
- اجرای `integrity_check` و `foreign_key_check` پس از هر migration.
- آزمون کامل UI → IPC → SQLite به‌جای اتکای صرف به mock Tauri.
- مقایسهٔ عددی خروجی پنج گزارش اصلی و چهار صورت تکمیلی با WebApp و محاسبهٔ دستی مستقل.
- اصلاح پیام‌های commit مبهم برای ردیابی تغییرات مالی.

## ۴. کنترل‌های اجراشده در آخرین بررسی محلی

| بررسی | نتیجه |
| --- | --- |
| `cargo fmt --check` | بدون اختلاف |
| `cargo clippy --all-targets -- -D warnings` | بدون هشدار |
| `cargo test` | ۲۰۶ قبول، ۰ شکست، ۲ مورد ignored |
| `npm run check:js` | ۴۹ فایل JavaScript معتبر |
| `npm run lint:js` | بدون خطا |
| `npm test` | ۱۹ آزمون قبول |
| `npm run test:e2e` | ۳۱ آزمون Playwright قبول |
| `npm run check:signoff` | مطابق انتظار ناموفق؛ وضعیت sign-off هنوز `pending` است |

> این اعداد از اجرای محلی روی کد جاری به‌دست آمده‌اند. آخرین اجرای CI تأییدشده مربوط به
> commit قبلی است و اجرای CI روی commit نهایی، همراه با Branch Protection، باید جداگانه
> تأیید شود. موفقیت آزمون‌های محلی جای تأیید حرفه‌ای حسابدار را نمی‌گیرد.

## ۵. موانع انتشار رسمی

- [ ] تأیید مستقل حسابدار/حسابرس و تکمیل `RELEASE-SIGNOFF` در
      [`Accounting-Report-Signoff.md`](Accounting-Report-Signoff.md).
- [ ] اجرای موفق کامل CI (`verify`، `ui-e2e`، `security-audit`، `desktop-build`)
      روی commit نهایی.
- [ ] ساخت واقعی Release با گواهی معتبر، امضای EXE و NSIS و کنترل `signtool verify`.
- [ ] فعال‌سازی Branch Protection/Ruleset برای `main` و الزام گذر از CI.
- [ ] آزمون بازیابی backup عادی و `.hacc` روی دستگاه دوم.
- [ ] ثبت نتیجهٔ benchmark دادهٔ حجیم (حداقل ۱۰۰ هزار و ۳۰۰ هزار ردیف).

## ۶. ترتیب پیشنهادی ادامهٔ کار

1. تکمیل تأیید مستقل حسابداری و بستن P1-04.
2. اجرای CI راه دور روی commit نهایی، رفع شکست‌ها و فعال‌سازی Branch Protection (P1-06).
3. تعیین سیاست نسخه‌بندی طبقه‌بندی حساب و جلوگیری از تغییر ناخواستهٔ گزارش‌های تاریخی (P1-02).
4. در صورت نیاز به تبادل داده با WebApp، تثبیت قرارداد تاریخ و DTO (P2-02 و P2-11).
5. اجرای benchmark واقعی و سپس تصمیم دربارهٔ Virtual Scrolling، Connection Pool،
   Streaming Excel و FTS5 (P2-10، P2-13، P2-14 و P2-15).
6. تفکیک تدریجی فایل‌های بزرگ UI و تکمیل آزمون چاپ/PDF واقعی (P2-09 و P2-12).
7. بستن تدریجی بک‌لاگ تکمیلی و آماده‌سازی Release امضاشده.
