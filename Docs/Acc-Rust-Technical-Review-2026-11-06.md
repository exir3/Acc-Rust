# گزارش بررسی فنی نرم‌افزار حسابداری Acc-Rust

**تاریخ بررسی:** ۶ نوامبر ۲۰۲۶  
**مخزن:** https://github.com/exir3/Acc-Rust  
**شاخه:** `main`  
**کامیت مبنای بررسی:** `bfb7dbb78c1897f8153de9df6fea393400a3d28d`  
**نوع بررسی:** بازبینی ایستای کد، معماری، پایگاه داده، منطق حسابداری، امنیت، آزمون‌ها و CI/CD

> این گزارش وضعیت کامیت مبنا را توصیف می‌کند. کد روی رایانه کاربر اجرا نشده و بررسی حاضر جایگزین آزمون پذیرش عملیاتی روی داده‌های واقعی و محیط Windows نیست. در هر مورد، یافته قطعی از پیشنهاد بهبود یا موضوع نیازمند تأیید تخصصی تفکیک شده است.
>
> **به‌روزرسانی پس از بررسی:** یافته‌های این گزارش روی کد صحت‌سنجی و موارد تأییدشده اعمال شدند. متن اصلی به‌عنوان سابقهٔ بررسی تاریخی حفظ شده و وضعیت هر finding در «پیوست — وضعیت اصلاحات پس از صحت‌سنجی» آمده است.

## ۱. خلاصه مدیریتی

Acc-Rust از نظر معماری پایه و تفکیک مسئولیت‌ها وضعیت مناسبی دارد. رابط کاربری با HTML/CSS/JavaScript در Tauri 2 اجرا می‌شود، فرمان‌های UI از لایه command در Rust عبور می‌کنند و عملیات SQLite، منطق حسابداری، گزارش‌ها و ورود و خروجی Excel در ماژول‌های جدا قرار دارند.

نکته مهم، وجود کنترل‌های سمت سرور/پایگاه داده است؛ از جمله اعتبارسنجی سند، کنترل تراز بدهکار و بستانکار، وضعیت سال مالی، حفاظت از سند دائمی، کنترل هم‌زمانی ویرایش، اعتبارسنجی سلسله‌مراتب حساب‌ها و ثبت رویدادهای حسابرسی. همچنین چند مورد مهم از گزارش فنی قبلی در کامیت‌های جدید اصلاح شده‌اند.

### وضعیت فعلی CI

آخرین اجرای بررسی‌شده برای کامیت مبنا، اجرای [CI شماره 42220700682](https://github.com/exir3/Acc-Rust/actions/runs/42220700682) در ۶ نوامبر ۲۰۲۶ است. هر چهار Job موفق بوده‌اند:

| Job | نتیجه | توضیح |
|---|---|---|
| `verify` | موفق | ۱۵ آزمون JavaScript، ۱۴۸ آزمون Rust موفق و یک آزمون Rust نادیده‌گرفته‌شده؛ همچنین fmt و clippy موفق |
| `ui-e2e` | موفق | ۱۶ آزمون Playwright موفق |
| `security-audit` | موفق | ممیزی npm و Cargo بدون آسیب‌پذیری مسدودکننده |
| `desktop-build` | موفق | ساخت برنامه Windows، راه‌اندازی واقعی Tauri/WebView2، ایجاد SQLite و ساخت نصاب NSIS |

**ملاحظه مهم:** سبز بودن CI به معنی امضاشده بودن فایل خروجی نیست. در همین اجرا، artifact با نام `windows-installer-unsigned` تولید شده و `release-metadata.json` وضعیت `NotSigned` را برای فایل‌های اجرایی ثبت کرده است. این خروجی برای تست مناسب است، اما نباید به‌عنوان نصاب رسمی امضاشده توزیع شود.

### اولویت‌های اصلی

1. سخت‌سازی خواندن هدر فایل پشتیبان رمزنگاری‌شده، به‌خصوص محدود کردن پارامترهای Argon2 پیش از اجرای KDF.
2. اصلاح نگهداری نامحدود فایل‌های snapshot پیش از حذف گروهی و مهاجرت حساب‌های سطح ۴.
3. افزودن آزمون‌های یکپارچگی UI با Tauri و SQLite واقعی؛ تست فعلی Playwright از mock بک‌اند استفاده می‌کند.
4. دریافت تأیید مستقل حسابدار/حسابرس برای fixture صورت‌های مالی پیش از انتشار عملیاتی.
5. تکمیل فرایند انتشار رسمی امضاشده و به‌روزرسانی گزارش فنی قدیمی داخل مخزن.

## ۲. محدوده بررسی و محدودیت‌ها

مسیرهای کلیدی بررسی‌شده:

- `ui/`: صفحات و فرم‌ها، پنجره پیش‌نمایش چاپ، تنظیمات، فرم حساب‌ها، فرم سند و wizard ورود Excel.
- `src-tauri/src/commands/`: فرمان‌های Tauri، کنترل پنجره مجاز، عملیات سند، حساب، گزارش، backup و restore.
- `src-tauri/src/db/`: اتصال SQLite، schema، migration، سال مالی، حساب‌ها، audit و backup/restore.
- `src-tauri/src/vouchers/`: اعتبارسنجی و ذخیره سند، حذف گروهی، import، محاسبات و گزارش‌ها.
- `src-tauri/src/excel/`: parser و writer فایل‌های Excel و ورود حساب و سند.
- `tests/`، `playwright.config.mjs`، `scripts/smoke-windows.mjs`، `.github/workflows/ci.yml`، `README.md` و مستندات حفاظت داده.

محدودیت‌ها:

- برنامه با داده واقعی کاربر اجرا نشده است.
- صحت خروجی گزارش‌ها با نمونه‌های مستقل یک مؤسسه حسابرسی یا مجموعه داده عملیاتی بزرگ بررسی نشده است.
- کارکرد چاپگر، چاپ PDF و کیفیت خروجی در نسخه نصب‌شده روی چند نسخه Windows و اندازه صفحه نمایش به‌صورت دستی آزموده نشده است.
- هیچ تغییری در مخزن اعمال نشده و شاخه یا فایل کاربر تغییر نکرده است.

## ۳. نقاط قوت معماری و پیاده‌سازی

### ۳-۱. تفکیک مناسب UI، منطق دامنه و ذخیره‌سازی

ساختار مخزن، مسئولیت‌های UI، command layer، ماژول‌های حسابداری و لایه SQLite را از هم جدا کرده است. این ساختار نگهداری فرم‌ها و تست منطق دامنه را نسبت به یک فایل یکپارچه آسان‌تر می‌کند.

**پیشنهاد:** این تفکیک حفظ شود؛ منطق مالی و قواعد اعتبارسنجی در Rust مرجع نهایی باقی بمانند و JavaScript عمدتاً مسئول نمایش، دریافت ورودی و تعامل کاربر باشد.

### ۳-۲. اعتبارسنجی سمت بک‌اند و SQLite

کنترل‌های مهمی مانند تراز سند، محدودیت مبلغ، حداقل و حداکثر ردیف‌ها، تاریخ سند، سطح و ارتباط حساب‌ها و وضعیت سند دائمی صرفاً به کنترل‌های HTML متکی نیستند. triggerهای SQLite نیز برخی قواعد را در سطح پایگاه داده اعمال می‌کنند.

**پیشنهاد:** هر قاعده تجاری مهم باید حداقل یک تست Rust داشته باشد و در مواردی که امکان دستکاری مستقیم DB وجود دارد، invariant متناظر در SQLite نیز حفظ شود.

### ۳-۳. حفاظت در برابر هم‌زمانی و retry

در ذخیره سند از `expected_updated_at` برای جلوگیری از بازنویسی تغییرات هم‌زمان استفاده شده و idempotency key از ثبت تکراری در retry یک عملیات جلوگیری می‌کند. این دو کنترل برای محیطی که چند پنجره برنامه هم‌زمان باز است اهمیت زیادی دارند.

### ۳-۴. SQLite و مهاجرت داده

پایگاه داده در پوشه داده کاربر ذخیره می‌شود؛ WAL، foreign keys و busy timeout فعال‌اند و مقدار `synchronous` به‌صورت محافظه‌کارانه روی سطح امن FULL باقی مانده است. انتقال پایگاه داده قدیمی با `VACUUM INTO` انجام می‌شود تا اطلاعات موجود در WAL نیز از دست نرود.

### ۳-۵. ورود Excel

برای فایل ورودی محدودیت حجم، ابعاد کاربرگ، حجم بازشده ZIP، تعداد ردیف و ستون و قالب کد حساب وجود دارد. نرمال‌سازی ارقام فارسی و عربی و تفاوت حروف «ی/ي» و «ک/ك» نیز پیش‌بینی شده است. همچنین کدهای دارای صفر ابتدایی یا بیش از ۱۵ رقم باید متنی باشند تا Excel دقت عددی آن‌ها را از بین نبرد.

### ۳-۶. پشتیبان و بازیابی

نسخه‌های داخلی حساس با manifest دارای HMAC و hash فایل بررسی می‌شوند. بازیابی نیز ابتدا نسخه ایمنی از پایگاه داده جاری می‌سازد و در صورت شکست تلاش می‌کند وضعیت قبلی را برگرداند. برای پشتیبان قابل‌انتقال، قالب رمزنگاری‌شده `.hacc` با AES-256-GCM و Argon2id اضافه شده است.

## ۴. یافته‌ها و پیشنهادهای اصلاحی

### P1 — مواردی که در صورت انتشار رسمی باید قبل از انتشار تعیین تکلیف شوند

در کامیت مبنا، نقصی مشاهده نشد که CI را متوقف کند یا آسیب‌پذیری High شناخته‌شده‌ای را در ممیزی جاری نشان دهد. با این حال، **توزیع عمومی نسخه به‌عنوان خروجی رسمی امضاشده تا زمان تکمیل تنظیمات گواهی و تأیید امضا توصیه نمی‌شود**؛ جزئیات در P2-06 آمده است. اگر سیاست محصول الزام به امضای کد دارد، این موضوع باید در دروازه انتشار رسمی P1 محسوب شود.

### P2-01 — پارامترهای Argon2 از هدر غیرقابل‌اعتماد فایل پذیرفته می‌شوند

**شدت:** متوسط تا بالا از منظر دسترس‌پذیری برنامه  
**فایل:** `src-tauri/src/db/portable.rs`  
**وضعیت:** نیازمند اصلاح

**مشاهده:**

قالب backup رمزنگاری‌شده، پارامترهای KDF را در هدر ذخیره می‌کند. کد فعلی اجازه می‌دهد `m_cost` تا `1024 * 1024` KiB، یعنی حدود یک گیگابایت حافظه، و `t_cost` تا ۱۰ و `p_cost` تا ۸ برسد. این مقادیر در `parse_header` کنترل می‌شوند، اما احراز اصالت AES-GCM هدر زمانی انجام می‌شود که عملیات KDF اجرا شده باشد. بنابراین فایل دست‌کاری‌شده می‌تواند مقادیر بسیار پرهزینه‌ای درخواست کند و پیش از رد شدن authentication باعث مصرف شدید RAM و CPU یا توقف پاسخ‌گویی برنامه شود.

**راهکار پیشنهادی:**

1. چون writer فعلی فقط از ترکیب ثابت `19 MiB / t=2 / p=1` استفاده می‌کند، در نسخه فعلی بهتر است پارامترهای هدر با یک allowlist محدود و مشخص تطبیق داده شوند، نه بازه‌ای تا ۱ GiB.
2. در صورت نیاز به پشتیبانی از نسخه‌های آینده، سقف حافظه و زمان KDF باید متناسب با حداقل سخت‌افزار پشتیبانی‌شده تعیین شود؛ افزایش این سقف باید همراه با تغییر نسخه قالب باشد.
3. همه محدودیت‌ها باید پیش از فراخوانی `derive_key` بررسی شوند.
4. برای هدرهای نامعتبر، قبل از اجرای Argon2 خطای سریع و کنترل‌شده برگردانده شود.
5. تستی بسازید که فایل با `m_cost` و `t_cost` در بیشترین مقدار مجاز فعلی را ایجاد کند و اثبات کند parser قبل از اجرای KDF آن را رد می‌کند.

**معیار پذیرش:** هیچ هدر غیرمجاز نتواند تخصیص حافظه KDF بزرگ یا زمان پردازش نامتعارف ایجاد کند؛ backupهای ساخته‌شده با نسخه جاری همچنان قابل بازیابی باشند.

### P2-02 — رمزنگاری و رمزگشایی backup کل فایل را در حافظه بارگذاری می‌کند

**شدت:** متوسط، مخصوصاً برای دیتابیس‌های بزرگ یا سیستم‌های کم‌حافظه  
**فایل:** `src-tauri/src/db/portable.rs`  
**وضعیت:** بهبود عملکرد و پایداری

**مشاهده:**

حداکثر اندازه plaintext برابر ۲ GiB تعریف شده است. با این حال، مسیر رمزنگاری از `std::fs::read` استفاده می‌کند و هم‌زمان buffer متن اصلی، خروجی رمزنگاری و buffer نهایی خروجی را ایجاد می‌کند. در رمزگشایی نیز فایل رمزنگاری‌شده و plaintext حاصل به‌طور کامل در حافظه قرار می‌گیرند. بنابراین برای فایل‌های بزرگ، اوج مصرف حافظه می‌تواند چند برابر حجم فایل شود.

**راهکار پیشنهادی:**

1. قالب پشتیبان را در نسخه بعدی به رمزنگاری قطعه‌ای (chunked AEAD) تغییر دهید؛ هر قطعه nonce/sequence و AAD مستقل داشته باشد تا حذف، جابه‌جایی یا تکرار قطعات قابل تشخیص باشد.
2. ابتدا فایل موقت در همان volume مقصد ایجاد شود؛ پس از تکمیل همه قطعات و تأیید tag نهایی، فایل به‌صورت اتمیک جایگزین شود.
3. برای سازگاری با قالب فعلی، decoder نسخه ۱ حفظ و decoder جدید برای نسخه ۲ اضافه شود.
4. تا زمان پیاده‌سازی streaming، سقف اندازه backup قابل‌انتقال بر اساس RAM واقعی سیستم پایین‌تر آورده شود و قبل از آغاز عملیات، اندازه فایل و حافظه موردنیاز تخمین زده شود.
5. تست فایل‌های بزرگ و قطع عملیات حین رمزنگاری/رمزگشایی اضافه شود؛ فایل ناقص نباید به‌عنوان backup معتبر باقی بماند.

**معیار پذیرش:** مصرف RAM با افزایش اندازه backup خطی و کنترل‌شده بماند و شکست عملیات، backup قبلی مقصد را خراب نکند.

### P2-03 — فایل‌های snapshot پیش از حذف گروهی و مهاجرت حساب‌ها مشمول retention نیستند

**شدت:** متوسط از منظر مصرف دیسک و نگهداری بلندمدت  
**فایل‌ها:** `src-tauri/src/db/backup.rs`، `src-tauri/src/vouchers/bulk_delete.rs`، `src-tauri/src/db/legacy.rs`  
**وضعیت:** یافته قطعی از الگوی نام‌گذاری و کد cleanup

**مشاهده:**

تابع `prune_backup_files` فقط فایل‌هایی را پاک‌سازی می‌کند که نامشان با `hesabdari-backup-` شروع و به `.sqlite3` ختم شود. اما حذف گروهی اسناد snapshotهایی با الگوی `pre_delete_...sqlite3` می‌سازد و مهاجرت حساب‌های سطح ۴ فایل‌هایی با الگوی `level4-migration-...sqlite3` در همان پوشه `backups` ایجاد می‌کند. در جست‌وجوی ارجاعات مخزن، مسیر cleanup برای این دو الگو مشاهده نشد. snapshotهای داخلی نیز فایل sidecar با پسوند `.manifest.json` دارند.

در نتیجه، با تکرار حذف‌های گروهی یا اصلاح حساب‌های legacy، فایل‌های SQLite و manifestهای متناظر می‌توانند بدون محدودیت روی دیسک باقی بمانند.

**راهکار پیشنهادی:**

1. سیاست نگهداری مستقلی تعریف کنید؛ مثلاً نگهداری تعداد مشخصی از snapshotهای پیش از حذف و snapshotهای مهاجرت حساب، با امکان تغییر مقدار از تنظیمات.
2. cleanup باید فایل SQLite و manifest متناظر آن را به‌صورت یک واحد حذف کند؛ حذف فایل اصلی و باقی‌ماندن manifest یا برعکس مجاز نباشد.
3. فایل‌های در حال استفاده یا snapshot آخرین عملیات نباید حذف شوند.
4. قبل از پاک‌سازی، گزارش تعداد و حجم فایل‌هایی که قرار است حذف شوند در log ثبت شود.
5. تستی بنویسید که برای هر الگوی نام، فایل‌های بیشتر از سقف ایجاد کند و بررسی کند فقط قدیمی‌ترین فایل‌های مجاز و sidecar متناظر آن‌ها حذف شوند.

**معیار پذیرش:** حجم پوشه پشتیبان در طول زمان محدود بماند و هیچ snapshot معتبر موردنیاز برای بازیابی زودتر از سیاست مصوب حذف نشود.

### P2-04 — آزمون‌های Playwright بک‌اند واقعی Tauri را اجرا نمی‌کنند

**شدت:** متوسط از منظر اطمینان یکپارچگی  
**فایل‌ها:** `README.md`، `scripts/smoke-windows.mjs`، `tests/e2e/mock-tauri.js`  
**وضعیت:** محدودیت پوشش آزمون، نه خطای قطعی برنامه

**مشاهده:**

تست‌های Playwright رابط را در Chromium و با mock درون‌صفحه‌ای برای Tauri اجرا می‌کنند. این تست‌ها برای رفتار DOM و تعامل کاربر ارزشمندند، اما مسیر واقعی IPC، serialize/deserialize داده‌ها، command registration، پنجره‌های native و SQLite واقعی را پوشش نمی‌دهند.

Smoke Test ویندوز برنامه واقعی را اجرا می‌کند، وجود فرایند WebView2 را بررسی می‌کند و ایجاد فایل SQLite را می‌سنجد؛ اما عملیات واقعی ساخت سند، ذخیره، نهایی‌سازی، ورود Excel، حذف گروهی، restore و چاپ را از داخل رابط اجرا نمی‌کند.

**راهکار پیشنهادی:**

1. مجموعه Playwright فعلی حفظ شود؛ این تست‌ها سریع و برای regression رابط مناسب هستند.
2. یک لایه integration test روی برنامه واقعی Tauri/Windows اضافه شود که حداقل ساخت سند، ویرایش با کنترل هم‌زمانی، نهایی‌سازی، گزارش تراز، ورود Excel و restore را با دیتابیس موقت اجرا کند.
3. در صورت محدودیت ابزار کنترل UI، تست commandها با `AppHandle` و SQLite موقت در Rust انجام و برای موارد واقعاً وابسته به WebView2 تست جدا تعریف شود.
4. در پایان تست، دیتابیس و پوشه موقت باید پاک شوند و هیچ مسیر داده واقعی کاربر استفاده نشود.
5. تست چاپ باید حداقل تولید DOM گزارش، باز شدن پنجره preview و چاپ/ذخیره PDF در Windows را جداگانه بررسی کند.

**معیار پذیرش:** حداقل یک مسیر عملیاتی کامل از UI تا فرمان Tauri و SQLite واقعی در CI ویندوز اجرا شود.

### P2-05 — fixture گزارش‌های مالی هنوز تأیید رسمی حسابدار/حسابرس ندارد

**شدت:** بالا از منظر پذیرش محصول حسابداری  
**فایل‌ها:** `src-tauri/src/vouchers/reports/fixtures/README.md`، `reference_tests.rs` و `financial_statements.rs`  
**وضعیت:** نیازمند تأیید متخصص، نه لزوماً اشکال در فرمول

**مشاهده:**

مخزن fixture مناسبی برای تراز آزمایشی، صورت سود و زیان و ترازنامه دارد. پوشش آن شامل بخش‌های جاری و غیرجاری، درآمد، هزینه، بهای تمام‌شده، درآمد/هزینه سایر، گروه‌های دوگانه ۱۰ و ۱۱، حساب‌های بدون تفصیلی و دارای تفصیلی، سند افتتاحیه و اختتامیه، اسناد موقت و رسمی، مرز سال مالی و تاریخ کبیسه است. ارقام مرجع نیز در مستند fixture آورده شده‌اند.

با این حال، مستند fixture صریحاً می‌گوید ارقام با روابط حسابداری مجموعه داده و بررسی کد تهیه شده‌اند و هنوز تأیید رسمی حسابدار/حسابرس را ندارند. در نرم‌افزار حسابداری، برابر بودن خروجی با fixture داخلی کافی نیست؛ ممکن است خود fixture یک فرض طبقه‌بندی نادرست را تثبیت کند.

**راهکار پیشنهادی:**

1. یک حسابدار ارشد یا حسابرس مستقل، ساختار حساب‌ها، مانده‌های افتتاحیه، گردش دوره، بستن حساب‌های موقت و قطعی و خروجی نهایی گزارش‌ها را بررسی کند.
2. خروجی مورد انتظار باید مستقل از اجرای کد محاسباتی برنامه محاسبه شود؛ از بازتولید fixture صرفاً با همان تابع گزارش‌ساز خودداری شود.
3. برای هر سناریو، سند مرجع، کدینگ، فرض طبقه‌بندی و خروجی تأییدشده نگهداری شود.
4. سناریوهای خاص کدینگ شرکت‌ها، حساب‌های با ماهیت دوگانه، حساب‌های دارای مانده غیرعادی و سال مالی غیرمتعارف به fixture افزوده شوند.
5. تأیید نهایی همراه با نام نقش تأییدکننده، تاریخ، نسخه برنامه و hash fixture در release checklist ثبت شود.

**معیار پذیرش:** پیش از انتشار عملیاتی، fixture توسط مسئول مالی/حسابرس تأیید و امضای تأیید در مستندات انتشار ثبت شود.

### P2-06 — آخرین artifact ساخته‌شده unsigned است؛ انتشار رسمی باید سخت‌گیرانه‌تر شود

**شدت:** بالا برای توزیع عمومی رسمی؛ متوسط برای buildهای آزمایشی  
**فایل:** `.github/workflows/ci.yml`  
**وضعیت:** بخشی از سازوکار امضا پیاده شده، اما آخرین خروجی بررسی‌شده امضا نشده است.

**مشاهده:**

Workflow امکان امضای فایل اجرایی برنامه و نصاب NSIS را دارد و در صورت وجود certificate، `signtool verify` را اجرا می‌کند. همچنین اجرای دستی با ورودی `release: true` در صورت نبود secret گواهی باید شکست بخورد. با این حال، در اجرای CI شماره 42220700682 متغیرهای گواهی خالی بوده‌اند و artifact با نام `windows-installer-unsigned` ساخته شده است؛ metadata نیز `signatureStatus: NotSigned` را ثبت کرده است.

Workflow فعلی artifact را در GitHub Actions بارگذاری می‌کند؛ انتشار نهایی در GitHub Releases یا کانال توزیع مشتری در این workflow دیده نمی‌شود.

**راهکار پیشنهادی:**

1. artifactهای push/PR به‌عنوان توسعه‌ای و unsigned باقی بمانند و برچسب واضح unsigned داشته باشند.
2. فرایند انتشار رسمی فقط از مسیر `workflow_dispatch` با `release: true` یا یک workflow مستقل release اجرا شود.
3. در release رسمی، وجود هر دو secret گواهی و رمز عبور الزامی باشد؛ امضای EXE و نصاب و تأیید `signtool verify /pa /v` اجباری باشد.
4. پس از verify، علاوه بر نصاب، در صورت نیاز محصول، فایل EXE مستقل نیز به artifact افزوده شود؛ اکنون artifact بارگذاری‌شده شامل نصاب و metadata است.
5. قبل از انتشار عمومی، hash نهایی فایل‌ها، thumbprint گواهی، وضعیت امضا، نسخه، commit و زمان build در release metadata ثبت و نگهداری شود.
6. اگر هدف انتشار در GitHub Releases است، مرحله ایجاد Release و بارگذاری artifact امضاشده پس از تمام کنترل‌ها اضافه شود؛ انتشار نباید با شکست هر تست یا امضا انجام شود.

**معیار پذیرش:** هیچ فایل unsigned از مسیر انتشار رسمی قابل دریافت نباشد؛ artifact توسعه‌ای و رسمی از نظر نام، metadata و کانال انتشار کاملاً قابل تشخیص باشند.

### P2-07 — پشتیبان‌های عادی SQLite رمزنگاری نمی‌شوند

**شدت:** وابسته به مدل تهدید و شیوه نگهداری داده  
**فایل‌ها:** `Docs/Data-Protection-and-Release-Policy.md`، `src-tauri/src/commands/database.rs`، `src-tauri/src/db/connection.rs`  
**وضعیت:** ریسک پذیرفته‌شده و مستند؛ نیازمند کنترل اجرایی

**مشاهده:**

پشتیبان عادی با پسوند `.sqlite3` شامل داده خام SQLite است. رمزنگاری AES-256-GCM فقط برای فایل قابل‌انتقال `.hacc` انجام می‌شود. مستند حفاظت داده نیز این موضوع را اعلام کرده و نگهداری backup عادی روی پوشه دارای ACL محدود و درایو رمزنگاری‌شده مانند BitLocker را توصیه کرده است.

در کد اتصال پایگاه داده، استفاده از مسیر AppData مشخص است؛ اما اعمال یا بررسی اختصاصی ACL پوشه backup و کلید HMAC در برنامه مشاهده نشد. حفاظت پیش‌فرض حساب ویندوز می‌تواند در سناریوی تک‌کاربره کافی باشد، ولی این فرض باید برای محیط استقرار واقعی بررسی شود.

**راهکار پیشنهادی:**

1. در نصب/اولین اجرا، مسیر داده و backup و سطح دسترسی واقعی پوشه بررسی شود؛ اگر دسترسی برای کاربران غیرمجاز وجود دارد، هشدار یا جلوگیری از ادامه انجام شود.
2. پشتیبان رمزنگاری‌شده به‌عنوان گزینه پیش‌فرض برای انتقال، ایمیل، فضای ابری یا رسانه قابل‌حمل معرفی شود.
3. برای backupهای خودکار نیز امکان رمزنگاری با DPAPI یا کلید حفاظت‌شده سیستم‌عامل ارزیابی شود.
4. کلید HMAC snapshot داخلی در برابر حذف/کپی ناخواسته محافظت و فرایند انتقال کامپیوتر به کامپیوتر برای آن مستند شود.
5. آزمون restore روی سیستم دوم با backup عادی و `.hacc` جداگانه انجام شود تا محدودیت portability روشن باشد.

**معیار پذیرش:** مستندات، UI و رفتار برنامه درباره تفاوت backup عادی و رمزنگاری‌شده هم‌راستا باشند و حفاظت پوشه داده در محیط هدف تأیید شود.

### P2-08 — نگاشت بخش گزارش در JavaScript و Rust تکرار شده است

**شدت:** متوسط رو به پایین؛ ریسک اختلاف تدریجی قواعد  
**فایل‌ها:** `ui/js/pages/settings.js` و `src-tauri/src/vouchers/accounting.rs`  
**وضعیت:** بهبود ساختاری

**مشاهده:**

کلیدهای بخش گزارش و طبقه‌بندی متناظر آن‌ها هم در `SECTION_CLASSES` و `GROUP_TYPE_CLASSES` سمت UI تعریف شده و هم در `section_of` و `classify_activity` سمت Rust. کامنت UI تصریح می‌کند که mapping باید با Rust هماهنگ باشد؛ اما تست parity مستقلی برای اثبات این هماهنگی مشاهده نشد.

**راهکار پیشنهادی:**

- یک metadata نسخه‌دار مشترک JSON برای کلیدها و labelها تعریف کنید و آن را در UI مصرف کنید؛ یا
- تستی بنویسید که فهرست کلیدهای UI و Rust و طبقه‌بندی هر کلید را مقایسه کند.
- منطق محاسبه صورت‌های مالی همچنان در Rust باقی بماند؛ فایل مشترک فقط metadata و نگاشت نمایشی باشد.

**معیار پذیرش:** افزودن/حذف/تغییر هر section بدون به‌روزرسانی هم‌زمان mapping متناظر، تست CI را fail کند.

## ۵. موارد نگهداری و بهبود با اولویت P3

### P3-01 — گزارش فنی موجود در مخزن از نظر خلاصه و نتیجه‌گیری به‌روز نیست

**فایل:** `Docs/Acc-Rust-Technical-Review-2026-11-06.md`

header سند می‌گوید گزارش تاریخی است و کامیت مبنای آن `0ec90cfa...` بوده؛ این نکته درست است. اما خلاصه مدیریتی، جدول CI، conclusion و بخشی از معیارهای پذیرش هنوز وضعیت قدیمی را نشان می‌دهند؛ از جمله ادعای شکست `cargo audit` و توقف desktop build. در حالی که آخرین کامیت و اجرای CI این موارد را رفع کرده‌اند.

**راهکار:**

- خلاصه و نتیجه‌گیری ابتدای سند با وضعیت HEAD فعلی جایگزین شود.
- findingهای رفع‌شده در جدول تاریخچه با وضعیت `Fixed` و لینک کامیت اصلاحی قرار گیرند.
- فقط موارد `Open`، `Partially Fixed`، `Accepted Risk` و `Needs Validation` در خلاصه مدیریتی دیده شوند.
- hash کامیت و شناسه run در هر نسخه گزارش صریح و قابل‌کلیک باشد.

### P3-02 — دو هشدار maintenance در ممیزی Rust باقی مانده‌اند

**شاهد:** لاگ `security-audit` در اجرای 42220700682

`cargo audit` با موفقیت تمام شده، اما دو هشدار پذیرفته‌شده گزارش کرده است:

- `proc-macro-error 1.0.4` با وضعیت unmaintained و شناسه `RUSTSEC-2024-0370`.
- `glib 0.18.5` با هشدار unsound درباره iterator و شناسه `RUSTSEC-2024-0429`.

این هشدارها در اجرای جاری آسیب‌پذیری High/Critical مسدودکننده گزارش نکرده‌اند، اما نباید بدون مالک و زمان بازبینی برای همیشه نادیده گرفته شوند.

**راهکار:** برای هر crate با `cargo tree -i <crate>` وابستگی والد مشخص شود؛ سپس ارتقای dependency والد، جایگزینی crate یا پذیرش ریسک مستند همراه با بررسی target ویندوز انجام شود. هشدار maintenance را با آسیب‌پذیری قابل‌استفاده در build نهایی یکی ندانید.

### P3-03 — GitHub Actions برای Node.js 20 هشدار deprecation می‌دهد

**فایل:** `.github/workflows/ci.yml`

لاگ اجرای فعلی هشدار می‌دهد `actions/checkout@v4`، `actions/setup-node@v4` و `actions/upload-artifact@v4` از runtime مبتنی بر Node 20 استفاده می‌کنند که در runner جاری به Node 24 منتقل شده است. این هشدار علت شکست CI نیست، اما احتمال تغییر رفتار یا توقف پشتیبانی در آینده وجود دارد.

**راهکار:** نسخه actionها به نسخه‌های رسمی سازگار با Node 24 ارتقا داده شوند؛ پس از تغییر، هر چهار Job روی Windows و Ubuntu دوباره اجرا شوند. نسخه actionها pin و با سیاست امنیت زنجیره تأمین مخزن هماهنگ باشد.

### P3-04 — تست دسترس‌پذیری و رفتار UI در scalingهای مختلف کامل نیست

تست Playwright فعلی برای تعاملات اصلی مفید است، اما پوشش مشخصی برای screen reader، ترتیب focus، پیمایش کامل با keyboard، high-DPI و scalingهای ۱۲۵٪ و ۱۵۰٪ در Windows مشاهده نشد.

**راهکار:** برای dialogها، gridها، انتخابگر حساب و فرم سند تست keyboard/focus و در صورت امکان axe یا ابزار مشابه اضافه شود. روی نمایشگرهای 1366×768، 1920×1080 و scalingهای رایج smoke UI اجرا شود.

### P3-05 — benchmark برای گزارش‌های حجیم ثبت نشده است

ساختار SQLite دارای index و queryهای گزارش‌محور است، اما معیار کارایی مستندشده برای تعداد زیاد سند و ردیف گزارش مشاهده نشد.

**راهکار:** دیتاست مصنوعی ۱۰۰ هزار و یک میلیون ردیفی تولید شود؛ زمان query، زمان render، حافظه مصرفی و query plan شاخص‌های اصلی ثبت شوند. تغییر index فقط با اندازه‌گیری قبل/بعد انجام شود.

## ۶. بررسی بخش‌های اصلی برنامه

### ۶-۱. فرانت‌اند

**ارزیابی:** ساختار ماژولار، فایل‌های وظیفه‌محور و جداسازی فرم سند از سایر صفحات مناسب است. ESLint نیز به CI اضافه شده و قواعدی مانند متغیر تعریف‌نشده، Promise و الگوهای ناامن DOM را بررسی می‌کند.

**بهبودهای پیشنهادی:**

- برای همه فرمان‌های حساس، خطای backend علاوه بر toast در خود فرم باقی بماند تا بعد از محو پیام قابل بازیابی باشد.
- در عملیات طولانی، وضعیت busy، لغو، موفقیت و شکست از یک state معتبر و شناسه عملیات تغذیه شود.
- تست keyboard و focus برای dialogها و فرم‌های چندبخشی افزوده شود.
- نگاشت‌های طبقه‌بندی در UI از منبع مشترک یا parity test تغذیه شوند.

### ۶-۲. بک‌اند Rust و لایه command

**ارزیابی:** محدودیت پنجره اجراکننده فرمان با `require_window`، توکن‌های کوتاه‌عمر برای بعضی عملیات preview/confirm، hash فایل در restore و ورود حساب، و ثبت audit در عملیات مهم، تصمیم‌های مناسبی هستند.

**بهبودهای پیشنهادی:**

- الگوی preview-token و hash برای تمام importها و عملیات مخرب حساس به‌صورت یکنواخت تعریف شود.
- برای عملیات طولانی، شناسه عملیات مستقل از عمر dialog تعریف شود تا progress/cancel/result به یک عملیات مشخص متصل باشد.
- در فرمان‌های محدود، به‌جای رشته آزاد از enumهای محدود Rust استفاده شود.
- آزمون‌های command در محیط Tauri واقعی برای کنترل مجوز پنجره‌ها و صحت payload اضافه شود.

### ۶-۳. SQLite و مدل داده

**ارزیابی:** WAL، foreign keys، busy timeout، migrationهای نسخه‌دار، transaction و triggerهای حفاظتی، پایه مناسبی ایجاد کرده‌اند. نسخه فعلی schema در `common.rs` برابر ۱۰ است.

**بهبودهای پیشنهادی:**

- بعد از هر migration مهم، `PRAGMA integrity_check` و `foreign_key_check` و invariantهای حسابداری در تست اجرا شوند.
- سناریوی هم‌زمانی دو پنجره برای ذخیره سند، تغییر سال مالی، restore و گزارش‌گیری با دیتابیس یکسان اضافه شود.
- تست بازیابی از فایل خراب، نسخه قدیمی، فایل ناقص و قطع عملیات اجرا شود.

### ۶-۴. حساب‌ها و سلسله‌مراتب

**ارزیابی:** کد حساب، سطح، گروه و parent در backend اعتبارسنجی می‌شوند. در import حساب از Excel، preview و token به فایل مشخص متصل شده و در زمان ثبت، hash دوباره کنترل می‌شود. این موضوع یکی از اصلاحات مهم اخیر است.

**بهبودهای پیشنهادی:**

- ابزار گزارش سلامت کدینگ شامل حساب‌های بدون parent معتبر، parent غیرفعال، سطح ناسازگار، گروه ناسازگار، حساب بدون گردش و ماهیت غیرعادی طراحی شود.
- تغییر گروه یا ماهیت حساب دارای گردش، با preview اثر بر گزارش‌ها و تأیید مسئول مالی همراه باشد.
- گزارش قبل/بعد مهاجرت حساب‌های legacy در قالب فایل قابل خروجی ارائه شود.

### ۶-۵. اسناد حسابداری

**ارزیابی:** بررسی تراز سند، مبلغ مثبت، بدهکار/بستانکار یک‌طرفه، تعداد ردیف، اعتبار تاریخ و وضعیت سال مالی در Rust انجام می‌شود. سند دائمی از طریق triggerهای SQLite در برابر تغییر و حذف محافظت می‌شود. کنترل `expected_updated_at` نیز برای ویرایش هم‌زمان مفید است.

**بهبودهای پیشنهادی:**

- property-based test برای مقادیر مرزی، overflow، تعداد بالای خطوط و ترکیب حساب/تفصیلی اضافه شود.
- تست هم‌زمانی ویرایش یک سند در دو پنجره واقعی اجرا شود.
- برای حذف یا انتقال اسناد، گزارش اثر قبل/بعد و مسیر بازیابی روشن در رابط نمایش داده شود.

### ۶-۶. گزارش‌ها و چاپ

**ارزیابی:** دفتر، تراز آزمایشی، صورت سود و زیان و ترازنامه در ماژول‌های مجزا قرار دارند. کنترل overflow در جمع‌ها انجام می‌شود و scope گزارش کاری/رسمی نیز در مدل وجود دارد. fixture مرجع گزارش‌ها پوشش مناسبی دارد.

**بهبودهای پیشنهادی:**

- تأیید مستقل fixture توسط حسابدار/حسابرس ضروری است.
- چاپ واقعی و PDF در WebView2 به Windows smoke/integration test افزوده شود.
- برای گزارش‌های سنگین benchmark و پایش query plan اضافه شود.

### ۶-۷. Excel

**ارزیابی:** نرمال‌سازی حروف فارسی و ارقام، محدودیت حجم فایل و آرشیو، کنترل ابعاد و اعتبارسنجی کدها مناسب است. ورود دسته‌جمعی سند، preview و کنترل گروه‌های حدس‌زده‌شده را دارد و انتخاب دستی کاربر در نگاشت گروه‌ها ثبت audit می‌شود.

**بهبودهای پیشنهادی:**

- تست منفی برای فایل‌های خراب، ZIP bomb، worksheetهای خالی یا با ابعاد غیرعادی، سلول merged، تاریخ شمسی نامعتبر، کد علمی/float و صفر ابتدایی گسترش یابد.
- در صورت پشتیبانی از فایل‌های بزرگ، parser و import به‌صورت مرحله‌ای و با progress قابل ردیابی اجرا شوند.
- خروجی import شامل فایل گزارش خطا با شماره ردیف اکسل باشد.

### ۶-۸. Backup و Restore

**ارزیابی:** backup SQLite از API پشتیبان‌گیری استفاده می‌کند؛ restore نسخه ایمنی ایجاد می‌کند و در صورت شکست بازیابی تلاش می‌شود نسخه قبلی بازگردد. فایل قابل‌انتقال `.hacc` با AES-256-GCM رمزنگاری می‌شود.

**بهبودهای پیشنهادی:**

- P2-01 و P2-02 در اولویت قرار گیرند.
- retention برای `pre_delete` و `level4-migration` و manifestهای متناظر اضافه شود.
- restore قبل از جایگزینی، خلاصه شرکت، سال مالی، تعداد سند و تاریخ آخرین فعالیت فایل backup را نشان دهد.
- پس از restore، مسیر safety copy و نتیجه integrity check به کاربر نمایش داده شود.

## ۷. اصلاحات مهمی که در کامیت‌های اخیر انجام شده‌اند

این موارد در مقایسه با گزارش تاریخی قبلی، اصلاح‌شده محسوب می‌شوند و نباید دوباره به‌عنوان ایراد باز گزارش شوند:

1. ارتقای `calamine` به نسخه ۰٫۳۸ و `tokio` به نسخه اصلاح‌شده؛ ممیزی فعلی دیگر آسیب‌پذیری High مسدودکننده گزارش نمی‌کند.
2. اتصال preview ورود حساب از Excel به token، مسیر canonical و SHA-256 فایل.
3. امکان اصلاح/تأیید دستی گروه‌های حدس‌زده‌شده در ورود دسته‌جمعی اسناد و ثبت تصمیم در audit.
4. اضافه شدن بررسی لغو در آخرین نقطه پیش از commit ورود دسته‌جمعی سند.
5. جلوگیری از بستن dialog ورود در زمانی که عملیات در حال اجرا است.
6. استفاده از manifest دارای HMAC برای snapshotهای داخلی.
7. اضافه شدن backup قابل‌انتقال رمزنگاری‌شده `.hacc` با AES-256-GCM و Argon2id.
8. اضافه شدن fixture گزارش‌های مالی، ESLint و آزمون واقعی راه‌اندازی Tauri/WebView2 در Windows.
9. تکمیل منطق اختیاری امضای EXE و نصاب و ثبت hash و وضعیت امضا در release metadata.

**خروجی مورد انتظار:** backup/restore در برابر فایل‌های مخرب یا بزرگ قابل‌پیش‌بینی و از نظر منابع کنترل‌شده باشد و پوشه backup بدون حد رشد نکند.

### فاز دوم — اطمینان حسابداری و یکپارچگی

1. دریافت تأیید رسمی fixture توسط حسابدار/حسابرس.

3. افزودن integration test واقعی Windows/Tauri/SQLite.

**خروجی مورد انتظار:** صحت محاسبات کلیدی و ارتباط UI با بک‌اند با تست مستقل قابل اثبات باشد.

### فاز سوم — انتشار و نگهداری

4. رفع یا تعیین مالک برای هشدارهای `proc-macro-error` و `glib`.
5. به‌روزرسانی GitHub Actions برای runtime پشتیبانی‌شده.
6. اصلاح خلاصه مدیریتی و conclusion گزارش فنی داخل مخزن.

**خروجی مورد انتظار:** artifact رسمی قابل اعتماد، قابل ردیابی و امضاشده باشد و مستندات با وضعیت واقعی کد تطبیق داشته باشند.

- [ ] رمزنگاری/رمزگشایی فایل بزرگ، مصرف حافظه کنترل‌شده دارد یا سقف فایل متناسب با منابع کاهش یافته است.
- [ ] retention برای snapshotهای `pre_delete`، `level4-migration` و manifestها وجود دارد.
- [ ] حداقل یک مسیر کامل UI → Tauri IPC → Rust → SQLite واقعی در CI ویندوز اجرا می‌شود.
- [ ] fixture گزارش‌های مالی تأیید مستقل حسابدار/حسابرس را دریافت کرده است.
- [ ] parity mapping بخش گزارش بین UI و Rust در CI کنترل می‌شود.
- [ ] backup عادی و رمزنگاری‌شده از نظر حفاظت و قابلیت انتقال به‌روشنی از هم متمایز هستند.

- [ ] گزارش فنی موجود در `Docs` با HEAD و آخرین CI همگام شده است.

## ۱۰. نتیجه نهایی

Acc-Rust پایه فنی خوبی برای یک نرم‌افزار حسابداری دسکتاپ دارد. معماری ماژولار، اعتبارسنجی سمت Rust، triggerهای SQLite، کنترل هم‌زمانی، ثبت رویدادها، import مبتنی بر preview، backup امن‌تر و آزمون‌های موجود نقاط قوت واقعی پروژه‌اند. آخرین CI نیز نشان می‌دهد که وضعیت فعلی از گزارش قدیمی بهتر است و ساخت Windows با موفقیت انجام می‌شود.

با این حال، برای استفاده عملیاتی در محیط مالی، اولویت بعدی نباید صرفاً افزودن قابلیت‌های جدید باشد. بهتر است ابتدا فرایند پشتیبان‌گیری در برابر فایل‌های دست‌کاری‌شده و بزرگ سخت‌سازی شود؛ سپس نگهداری فایل‌های snapshot سامان یابد؛ بعد صحت گزارش‌ها با تأیید حسابدار/حسابرس و آزمون یکپارچگی واقعی تثبیت شود. در نهایت، انتشار رسمی باید با گواهی امضای معتبر و مستندات همگام انجام شود.

**جمع‌بندی:** وضعیت فعلی برای ادامه توسعه و آزمون مناسب است؛ انتشار رسمی برای مشتریان باید به تکمیل کنترل‌های P2-01، P2-03، P2-04، P2-05 و P2-06 و ثبت پذیرش ریسک‌های باقی‌مانده مشروط شود.

**آزمون‌های اعتبارسنجی روی همین تغییرات:**

- `cargo fmt --check` موفق.
- `cargo clippy --all-targets --all-features` بدون خطا؛ فقط هشدارهای از قبل موجود.
- `cargo test` با ۱۵۲ تست موفق و ۱ تست کمکی `ignored`.
- `npm run check:js` روی ۴۵ فایل و `npm run lint:js` بدون خطا.
- `npm test` با ۱۵ تست موفق و `npm run test:e2e` با ۱۸ تست موفق Playwright.
- `npm run test:smoke:windows` روی build debug واقعی Tauri/WebView2 موفق بود؛ SQLite موقت ساخته و اعتبارسنجی شد.

**تست‌های regression افزوده‌شده:**

- `header_accepts_only_the_writer_kdf_allowlist`: هر ترکیب KDF خارج از allowlist را پیش از استخراج کلید رد می‌کند.
- `decrypt_rejects_a_tampered_expensive_header_before_key_derivation`: هدر دست‌کاری‌شده با پارامترهای پرهزینه پیش از اجرای Argon2 رد می‌شود.
- `snapshot_retention_prunes_old_pre_delete_and_migration_pairs`: فقط قدیمی‌ترین snapshotهای مجاز و manifest متناظرشان حذف می‌شوند.
- `report_section_mapping_matches_ui`: نگاشت section و group type بین UI و Rust دقیقاً یکسان است.

**موارد باقی‌مانده پیش از انتشار رسمی:** تأیید مستقل fixture گزارش‌ها (P2-05)، اجرای واقعی مسیر امضا با گواهی معتبر و ایجاد GitHub Release، تکمیل آزمون یکپارچگی UI→Tauri→SQLite (P2-04)، تعیین تکلیف هشدارهای maintenance (P3-02)، و اعتبارسنجی ACL/رمزنگاری پوشهٔ داده در محیط هدف (P2-07).
