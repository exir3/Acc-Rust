## ۱. خلاصه مدیریتی

Acc-Rust یک نرم‌افزار حسابداری دسکتاپ مبتنی بر **Tauri 2، Rust، JavaScript و SQLite** است. تفکیک لایه رابط کاربری، فرمان‌های Tauri، منطق حسابداری و دسترسی به پایگاه داده از نقاط قوت ساختار فعلی است. در کد، کنترل‌هایی برای تراز سند، ساختار و ارتباط حساب‌ها، اعتبار دوره مالی، حفاظت از اسناد دائمی، کنترل هم‌زمانی، جلوگیری از ثبت تکراری و ثبت رویدادهای حسابرسی دیده می‌شود.

مهم‌ترین مانع جاری، **شکست Smoke Test برنامه واقعی Tauri/WebView2 در آخرین اجرای CI ارجاع‌شده** است. علت ریشه‌ای در لاگ موجود قابل اثبات نیست؛ فقط مشخص است که برنامه در مهلت ۶۰ ثانیه پایگاه داده آزمایشی را در مسیر موقت ایجاد نکرده است. در همین بازبینی، ابزار تشخیص خطا در دو سمت اضافه شد (ثبت خطای راه‌اندازی در فایل موقت و `stderr`، نمایش مسیر مؤثر داده، و خواندن همان لاگ توسط Smoke Test). این تغییر **علت را برطرف نمی‌کند** و تا اجرای موفق مجدد CI، این یافته «نیمه‌اصلاح‌شده» است.

## ۴. یافته‌های با اولویت بالا (P1)

### P1-01 — شکست Smoke Test برنامه واقعی در آخرین CI

**وضعیت:** ایراد قطعی در زنجیره CI؛ ابزار تشخیص اصلاح شد، علت ریشه‌ای هنوز اثبات نشده است.  
**شواهد:** [لاگ اجرای CI](https://github.com/exir3/Acc-Rust/actions/runs/42231055124) (بدون تأیید مجدد در این محیط)  
**فایل‌های مرتبط:**

- `scripts/smoke-windows.mjs`
- `src-tauri/src/db/connection.rs`
- `src-tauri/src/lib.rs`
- `.github/workflows/ci.yml`

**مشاهده:**

در Job مربوط به `desktop-build`، هر دو مرحله ساخت فایل اجرایی Release و ساخت Debug موفق بوده‌اند. اما اجرای برنامه واقعی با فرمان زیر:

```powershell
node scripts/smoke-windows.mjs --exe src-tauri/target/debug/Hesabdari.exe
```

به خطای زیر رسیده است:

```text
Tauri app did not create ...\hesabdari.sqlite3 within 60000ms.
The executable must be a debug build that honors HESABDARI_SMOKE_DATA_DIR.
```

در نتیجه مراحل امضای EXE، ساخت NSIS، امضای نصاب و بارگذاری artifact اجرا نشده‌اند.

این موضوع Regression یا ناپایداری در Smoke Test را مطرح می‌کند، ولی علت اصلی اثبات نشده است. در اجرای قبلی CI با شناسه `42220700682` همین Smoke Test موفق بوده است. بررسی کد نشان داد اسکریپت Smoke از قبل خروج زودهنگام process و `stderr` را تشخیص می‌دهد؛ شکاف واقعی این بود که `lib.rs` هنگام شکست `db::initialize` فقط یک پنجره گرافیکی نمایش می‌داد و هیچ نشانه‌ای برای CI یا log باقی نمی‌گذاشت.

**اصلاح اعمال‌شده در این بازبینی:**

1. در `src-tauri/src/lib.rs`، هنگام خطای راه‌اندازی، متن خطا همراه نسخه و وضعیت `HESABDARI_SMOKE_DATA_DIR` در `%TEMP%/hesabdari-startup-error.log` نوشته می‌شود و همان متن به `stderr` نیز چاپ می‌شود.
2. در `src-tauri/src/db/connection.rs` و فقط در build اشکال‌زدایی، مسیر مؤثر پوشه داده، مسیر SQLite و مقدار override چاپ می‌شود.
3. در `scripts/smoke-windows.mjs`، لاگ قدیمی قبل از اجرا حذف می‌شود و در همه مسیرهای شکست (خروج زودهنگام، timeout، خطای پس از ساخت DB و خطای پس از WebView2) محتوای log راه‌اندازی به پیام خطا افزوده می‌شود.

**راهکار باقی‌مانده:**

1. اجرای مجدد CI روی Windows runner و ثبت علت واقعی شکست از لاگ جدید.
2. اجرای چندباره Smoke Test برای رد ناپایداری تصادفی؛ تست حذف یا غیرفعال نشود.
3. تشخیص زودهنگام‌تر حالت «پنجره modal باز شده ولی DB ساخته نشده» با timeout کوتاه‌تر یا بررسی process/window.
4. اطمینان از اینکه هیچ مسیر داده واقعی کاربر در اجرای Smoke استفاده نمی‌شود (اکنون با override فقط‌در‌debug تأمین می‌شود).

**معیار پذیرش:** برنامه واقعی Tauri اجرا شود، WebView2 به‌عنوان فرایند فرزند راه‌اندازی شود و SQLite معتبر در پوشه موقت ساخته شود؛ در صورت شکست، علت ریشه‌ای در log قابل ردیابی باشد.

### P1-02 — حفاظت شاخه اصلی و الزام CI در سطح GitHub

**وضعیت:** نیازمند تصمیم و تنظیم مخزن؛ در این محیط قابل تأیید مجدد نبود.  
**شاهد نقل‌شده:** در گزارش قبلی آمده است پاسخ GitHub برای `branches/main` مقدار `protected: false` و `protection.enabled: false` را برگردانده است. این مشاهده درباره Branch Protection کلاسیک است؛ وجود یا نبود Ruleset جداگانه باید در تنظیمات مخزن نیز کنترل شود.

**ریسک:** اگر ادغام یا push مستقیم بدون الزام گذر از CI امکان‌پذیر باشد، commitی می‌تواند وارد `main` شود که آزمون‌ها یا build آن شکست خورده‌اند. در پروژه حسابداری، این موضوع به‌ویژه برای تغییرات مربوط به ثبت سند، سال مالی، backup و گزارش‌ها مهم است.

**راهکار پیشنهادی:**

1. برای `main` یک Ruleset یا Branch Protection فعال شود.
2. ادغام Pull Request به گذر موفق jobهای `verify`، `ui-e2e`، `security-audit` و `desktop-build` وابسته باشد.
3. حداقل یک تأیید بازبینی برای تغییرات حساس اجباری شود.
4. force push و حذف شاخه اصلی محدود شود.
5. برای تغییرات مربوط به `db/schema.rs`، `vouchers/`، گزارش‌های مالی و backup، بازبینی تخصصی کد الزامی شود.

**معیار پذیرش:** هیچ تغییری بدون گذر از کنترل‌های CI و بازبینی مصوب وارد شاخه اصلی نشود.

## ۵. یافته‌های با اولویت متوسط (P2)

### P2-01 — آزمون یکپارچگی کامل UI تا SQLite واقعی وجود ندارد

**وضعیت:** شکاف پوشش آزمون؛ نه خطای قطعی منطق برنامه.  
**فایل‌های مرتبط:** `tests/e2e/mock-tauri.js`، `tests/e2e/`، `scripts/smoke-windows.mjs` و `README.md`

**مشاهده:**

آزمون‌های Playwright رابط را در DOM واقعی اجرا می‌کنند، اما فرمان‌های Tauri با mock جایگزین شده‌اند. Smoke Test واقعی Windows/Tauri/WebView2 فقط راه‌اندازی برنامه، ایجاد SQLite و وجود فرایند WebView2 را تأیید می‌کند؛ چرخه کامل عملیات حسابداری را از UI واقعی اجرا نمی‌کند.

بنابراین ترکیب فعلی آزمون‌ها مفید است، ولی هماهنگی نام و آرگومان فرمان‌های JavaScript با Rust، رویدادهای IPC، رفتار پنجره‌های واقعی، file picker، تراکنش SQLite از مسیر UI و چاپ در WebView2 به‌صورت کامل پوشش داده نمی‌شود.

**راهکار پیشنهادی:**

1. آزمون‌های mock فعلی حفظ شوند؛ برای Regression سریع رابط ارزشمندند.
2. یک لایه Integration Test روی Windows/WebView2 ایجاد شود که از UI واقعی و دیتابیس آزمایشی استفاده کند.
3. حداقل سناریوها شامل ایجاد، ذخیره، بازکردن، ویرایش، دائمی‌سازی و حذف سند باشد.
4. ورود Excel، لغو ورود، اصلاح نگاشت گروه حساب، حذف گروهی و بازیابی backup نیز در سناریوهای مستقل پوشش داده شوند.
5. گزارش تراز آزمایشی، صورت سود و زیان، ترازنامه، بازکردن preview و تولید خروجی چاپ آزمایش شود.
6. آزمون مهاجرت از حداقل یک نسخه قدیمی schema به schema جاری افزوده شود.
7. تمام تست‌ها از پوشه داده و SQLite موقت استفاده کنند و پاک‌سازی داده آزمایشی در مسیر موفقیت و شکست تضمین شود.

**معیار پذیرش:** CI علاوه بر mock E2E و آزمون‌های Rust، حداقل یک چرخه عملیاتی واقعی UI→IPC→Tauri→SQLite را روی Windows اجرا کند.

### P2-02 — fixture گزارش‌های مالی هنوز تأیید مستقل حسابدار/حسابرس ندارد

**وضعیت:** نیازمند اعتبارسنجی تخصصی پیش از انتشار عملیاتی.  
**فایل‌های مرتبط:**

- `src-tauri/src/vouchers/reports/fixtures/README.md`
- `src-tauri/src/vouchers/reports/reference_tests.rs`
- `src-tauri/src/vouchers/reports/financial_statements.rs`
- `src-tauri/src/vouchers/reports/trial_balance.rs`

**مشاهده:**

پروژه یک مجموعه داده مرجع دارد که بخش‌های مختلف گزارش، گروه‌های دوگانه، حساب‌های با ماهیت بدهکار/بستانکار/دوگانه، تفصیلی، افتتاحیه، اسناد موقت و دائمی، اختتامیه و مرز سال مالی را پوشش می‌دهد. تست‌ها خروجی را دقیقاً با fixture ثابت مقایسه می‌کنند؛ این یک نقطه قوت است.

با این حال، خود مستند fixture تصریح می‌کند که خروجی هنوز تأیید رسمی حسابدار/حسابرس را دریافت نکرده است. تستی که خروجی برنامه را با fixture مقایسه می‌کند، صحت محاسبه مستقل fixture را اثبات نمی‌کند؛ ممکن است فرض اشتباه در fixture تثبیت شده باشد.

**راهکار پیشنهادی:**

1. یک حسابدار ارشد یا حسابرس مستقل، کدینگ، مانده‌های افتتاحیه، گردش‌ها، اختتامیه موقت/قطعی و خروجی سه گزارش را بررسی کند.
2. ارقام مورد انتظار خارج از توابع گزارش‌ساز برنامه محاسبه و تأیید شوند.
3. برای هر سناریو، اسناد نمونه، فرض طبقه‌بندی و محاسبات دستی نگهداری شود.
4. سناریوهای کدینگ سفارشی، حساب‌های با ماهیت دوگانه، مانده‌های غیرعادی و چند سال مالی به مجموعه مرجع اضافه شوند.
5. تأییدیه با تاریخ، نسخه برنامه و hash فایل fixture در release checklist ثبت شود.

**معیار پذیرش:** fixture قبل از استفاده عملیاتی توسط مسئول مالی/حسابرس تأیید و مستند شود. در این بررسی خطای عددی مشخصی در محاسبات گزارش‌ها اثبات نشده است.

### P2-03 — رمزنگاری backup قابل‌انتقال کل فایل را در حافظه بارگذاری می‌کند

**وضعیت:** کاهش ریسک انجام شده؛ بهبود معماری همچنان لازم است.  
**فایل:** `src-tauri/src/db/portable.rs`

**مشاهده:**

قالب `.hacc` از AES-256-GCM و Argon2id استفاده می‌کند. پارامترهای Argon2 پیش از اجرای KDF به یک allowlist ثابت محدود شده‌اند (`19 MiB / t=2 / p=1`) تا هدر دستکاری‌شده نتواند تخصیص حافظه بسیار بالا درخواست کند. سقف داده نیز به ۵۱۲ مگابایت کاهش یافته است (`MAX_PLAINTEXT_BYTES`).

با این حال، رمزنگاری و رمزگشایی همچنان از روش one-shot استفاده می‌کند و کل فایل با `std::fs::read` در حافظه قرار می‌گیرد. برای فایل نزدیک سقف، حافظه مصرفی لحظه‌ای می‌تواند چند برابر اندازه فایل باشد؛ به‌خصوص به دلیل نگهداری هم‌زمان plaintext، ciphertext و buffer خروجی.

**راهکار پیشنهادی:**

1. در نسخه بعدی قالب، رمزنگاری قطعه‌ای و authenticated streaming طراحی شود.
2. هر قطعه nonce/sequence مستقل و AAD شامل نسخه قالب، شماره قطعه و شناسه backup داشته باشد تا حذف، جابه‌جایی یا تکرار قطعات تشخیص داده شود.
3. خروجی ابتدا در فایل موقت نوشته و پس از تکمیل و اعتبارسنجی tag نهایی به‌صورت اتمیک جایگزین شود.
4. decoder نسخه ۱ برای سازگاری با backupهای قبلی حفظ شود و قالب streaming در نسخه ۲ معرفی شود.
5. تا زمان پیاده‌سازی، سقف ۵۱۲ مگابایت حفظ و پیش از عملیات، فضای دیسک و حافظه موردنیاز تخمین زده شود.

**معیار پذیرش:** مصرف RAM در فایل‌های بزرگ کنترل‌شده باشد و قطع عملیات، فایل backup قبلی یا پایگاه داده فعال را خراب نکند.

### P2-04 — backupهای عادی SQLite رمزنگاری نشده‌اند

**وضعیت:** ریسک پذیرفته‌شده و مستند؛ نیازمند کنترل اجرایی در محیط نصب.  
**فایل‌های مرتبط:** `src-tauri/src/commands/database.rs`، `src-tauri/src/db/connection.rs`، `src-tauri/src/db/backup.rs` و `Docs/Data-Protection-and-Release-Policy.md`

**مشاهده:**

پشتیبان قابل‌انتقال رمزنگاری‌شده با پسوند `.hacc` وجود دارد، ولی backup عادی `.sqlite3` یا `.db` داده خام SQLite است. مستند سیاست حفاظت داده نیز این تفاوت را توضیح می‌دهد و حفاظت پوشه با ACL ویندوز/BitLocker را توصیه می‌کند.

در کد بررسی‌شده، سازوکار اختصاصی که ACL پوشه داده، فایل backup و کلید `snapshot-integrity.key` را ایجاد یا در زمان اجرا بررسی کند مشاهده نشد. این امر به معنی دسترسی عمومی قطعی نیست؛ حفاظت پیش‌فرض AppData ویندوز ممکن است در نصب تک‌کاربره مناسب باشد، اما باید در محیط مقصد تأیید شود.

**راهکار پیشنهادی:**

1. در اولین اجرا یا نصب، ACL پوشه داده و backup بررسی و فقط به کاربر/گروه‌های مجاز محدود شود.
2. در رابط کاربری، کنار backup عادی هشدار داده شود که فایل قابل خواندن با SQLite است و برای انتقال باید از `.hacc` استفاده شود.
3. برای backupهای خودکار، رمزنگاری با DPAPI یا کلید حفاظت‌شده توسط سیستم‌عامل ارزیابی شود.
4. کلید HMAC داخلی، فایل manifest و backupها در یک مسیر امن با مجوزهای مناسب نگهداری شوند.
5. آزمون انتقال backup عادی و `.hacc` به دستگاه دوم و بازیابی هر دو انجام شود؛ محدودیت portability کلید snapshot داخلی مستند شود.

**معیار پذیرش:** رفتار UI و مستندات درباره تفاوت دو نوع backup شفاف باشد و ACL در محیط نصب واقعی آزمون شود.

### P2-05 — آخرین build موفق بدون امضای دیجیتال بوده و فرایند Release کامل نشده است

**وضعیت:** بخشی از سازوکار امضا پیاده شده؛ اعتبارسنجی انتشار رسمی هنوز کامل نیست.  
**فایل:** `.github/workflows/ci.yml` و `Docs/Data-Protection-and-Release-Policy.md`

**مشاهده:**

Workflow فعلی ساخت را به شکل دو مرحله‌ای اجرا می‌کند: build فایل اجرایی، امضای EXE در صورت وجود گواهی، ساخت NSIS بدون binary patching، امضای نصاب و بررسی Authenticode. metadata نیز hash و وضعیت واقعی امضای فایل‌ها را ثبت می‌کند و در اجرای رسمی `release: true` نبود گواهی را خطا تلقی می‌کند. `desktop-build` به هر سه Job قبلی وابسته است.

این طراحی مناسب است؛ اما آخرین CI ارجاع‌شده روی HEAD پیش از مرحله bundle و امضا شکست خورده است. در اجرای قبلی موفق `42220700682`، متغیرهای گواهی خالی بوده‌اند و artifact با وضعیت unsigned تولید شده است. علاوه بر آن، اجرای واقعی مسیر امضا با گواهی معتبر و مرحله ایجاد GitHub Release/بارگذاری artifact رسمی هنوز تأیید نشده است.

**راهکار پیشنهادی:**

1. buildهای push/PR به‌عنوان خروجی توسعه‌ای unsigned باقی بمانند و نام/metadata آن‌ها این موضوع را صریح نشان دهد.
2. مسیر Release رسمی فقط با `release: true` و وجود هر دو secret گواهی و رمز اجرا شود.
3. امضای EXE و نصاب با `signtool verify /pa /v` کنترل شود.
4. یک اجرای واقعی workflow با گواهی معتبر و timestamping انجام شود؛ صرف بررسی منطقی YAML کافی نیست.
5. پس از موفقیت همه تست‌ها، مرحله ایجاد GitHub Release و بارگذاری artifact رسمی امضاشده اضافه شود.
6. hash SHA-256، شماره نسخه، commit SHA، thumbprint گواهی و وضعیت امضا در Release metadata ثبت شوند.

**معیار پذیرش:** هیچ artifact unsigned از مسیر انتشار رسمی مشتری قابل دریافت نباشد؛ build آزمایشی و Release رسمی از نظر نام، metadata و کانال انتشار از هم جدا باشند.

## ۶. موارد بهبود و نگهداری با اولویت پایین‌تر (P3)

### P3-01 — هشدارهای مجاز وابستگی Rust باید مالک و مهلت بازبینی داشته باشند

**وضعیت:** باز؛ وابسته به زنجیره GTK/Linux، نه build ویندوز.

**شاهد و راستی‌آزمایی محلی:** اجرای `cargo audit --file src-tauri/Cargo.lock` با موفقیت (exit 0) روی ۴۶۶ وابستگی انجام شد و فقط دو هشدار گزارش کرد:

- `proc-macro-error 1.0.4` — `RUSTSEC-2024-0370`، وضعیت unmaintained.
- `glib 0.18.5` — `RUSTSEC-2024-0429`، وضعیت unsound برای iterator مربوط به `glib::VariantStrIter`.

بررسی `cargo tree --target all -i proc-macro-error` و `cargo tree --target all -i glib` نشان داد هر دو وابستگی فقط از مسیر GTK/Linux (زنجیره Tauri در لینوکس) وارد می‌شوند و در build ویندوز استفاده نمی‌شوند. بنابراین این هشدارها مانع CI نیستند، ولی نباید بدون مالک و تاریخ بازبینی رها شوند.

**راهکار:** مسیر والد را مستند کنید؛ سپس ارتقای dependency والد، جایگزینی crate یا پذیرش ریسک مستند با مالک و تاریخ بازبینی انجام شود. هشدار maintenance را با آسیب‌پذیری قابل بهره‌برداری در Windows یکی ندانید.

### P3-02 — پوشش دسترس‌پذیری و Windows scaling کامل نیست

در ساختار آزمون‌های موجود، پوشش روشن و مستقل برای ترتیب focus، پیمایش کامل با صفحه‌کلید، screen reader، contrast و مقیاس‌بندی Windows در ۱۲۵٪ و ۱۵۰٪ مشاهده نشد.

**راهکار:** برای dialogها، انتخابگر حساب، جدول سند، فرم حساب و گزارش تراز تست keyboard/focus اضافه شود. سناریوهای UI روی اندازه‌های 1366×768 و 1920×1080 و scalingهای رایج Windows آزمایش شوند. در صورت امکان ابزار accessibility مانند axe به تست‌ها اضافه شود.

### P3-03 — benchmark و سنجش کارایی روی داده حجیم وجود ندارد

در `ui/js/pages/trial-balance.js`، گزارش تراز آزمایشی در زمان بارگذاری با `showZero: true` و `multiLevel: true` درخواست می‌شود و بخشی از فیلترها و drill-down در سمت UI اعمال می‌شود. این کار برای تعامل و نمایش درختی مناسب است، اما روی کدینگ و پایگاه داده بزرگ ممکن است هزینه انتقال داده و رندر را بالا ببرد.

**راهکار:**

1. دیتاست مصنوعی با ۱۰۰ هزار، ۵۰۰ هزار و یک میلیون ردیف سند تولید شود.
2. زمان SQL، زمان آماده‌سازی داده در Rust، زمان انتقال IPC، زمان render و حافظه مصرفی جداگانه اندازه‌گیری شود.
3. `EXPLAIN QUERY PLAN` و indexهای مسیرهای پرتکرار بررسی شوند.
4. اگر bottleneck تأیید شد، pagination سمت بک‌اند، فیلترگذاری SQL و virtual scrolling در UI اضافه شود؛ از بهینه‌سازی حدسی و افزودن index بدون benchmark خودداری شود.

### P3-04 — ساختار JavaScript و CSS در فرم‌های بزرگ همچنان قابل ماژولارسازی بیشتر است

فرانت‌اند از فایل‌های ماژولار تشکیل شده، اما برخی فایل‌ها هنوز مسئولیت‌های متعدد و حجم قابل توجه دارند؛ از جمله `ui/js/menubar.js`، `ui/account-definition.js`، `ui/js/pages/settings.js`، `ui/js/pages/trial-balance.js` و `ui/styles.css`.

**راهکار:**

- توابع مشترک نمایش خطا، قالب‌بندی ارقام، تاریخ شمسی و ساخت dialog در ماژول‌های مشترک نگهداری شوند.
- قواعد و منطق کسب‌وکار همچنان در Rust مرجع نهایی باقی بمانند.

### P3-05 — fingerprint ورود گروهی از FNV-1a 64-bit استفاده می‌کرد

**وضعیت:** **Fixed**  
**فایل:** `src-tauri/src/vouchers/import.rs`

**مشاهده قبلی:** تابع `import_payload_hash` از FNV-1a 64-bit برای fingerprint محتوای فایل استفاده می‌کرد و نتیجه در `import_batches` ذخیره می‌شد. FNV برای hash سریع و غیرامنیتی مناسب است، اما مقاومت رمزنگارانه در برابر collision ندارد.

**اصلاح اعمال‌شده:**

1. fingerprint جدید با SHA-256 و پیشوند نسخه `sha256-v1:` تولید می‌شود.
2. fields با length-prefix در یک canonical stream نوشته می‌شوند تا مرزهای فیلد قابل جابه‌جایی نباشند.
3. هنگام بررسی replay، هم hash جدید و هم hash قدیمی FNV جست‌وجو می‌شود (`payload_hash IN (?1, ?2)`) تا batchهای ثبت‌شده قبل از ارتقا دوباره وارد نشوند.
4. دو تست اضافه شد: `import_payload_hash_is_versioned_sha256_and_detects_small_changes` و `legacy_fnv_import_batch_is_still_treated_as_a_replay`.

**معیار پذیرش:** payload یکسان hash یکسان بدهد، تغییر جزئی hash را تغییر دهد، و رکورد قدیمی FNV همچنان به‌عنوان replay شناسایی شود. هر دو تست محلی موفق‌اند.

## ۷. بک‌لاگ یکپارچهٔ موارد باز ادغام‌شده از گزارش‌های قبلی

این موارد در گزارش‌های قبلی به‌صورت پراکنده یا در بخش «بهبودهای پیشنهادی» آمده بودند و در کد جاری به‌عنوان یافتهٔ باز باقی‌اند. برای جلوگیری از تکرار، اینجا با شناسه `B-xx` نگهداری می‌شوند.

### B-01 — خلاصه پیش از Restore و نتیجه پس از آن

اکنون `choose_restore_backup` فقط `token`، `encrypted` و `file_name` برمی‌گرداند. کاربر پیش از جایگزینی پایگاه داده، خلاصهٔ شرکت، سال مالی، تعداد سند و تاریخ آخرین فعالیت فایل backup را نمی‌بیند و پس از بازیابی فقط مسیر safety copy را دریافت می‌کند.

**پیشنهاد:** پیش از restore، خلاصهٔ ساختار و محتوای فایل نمایش داده شود؛ پس از restore، مسیر safety copy، نتیجهٔ `integrity_check` و `foreign_key_check` به کاربر نشان داده شود.

### B-02 — گزارش سلامت کدینگ حساب‌ها

ابزار یا گزارش مستقل برای شناسایی حساب‌های بدون parent معتبر، parent غیرفعال، سطح ناسازگار، گروه ناسازگار، حساب بدون گردش و ماهیت غیرعادی وجود ندارد.

**پیشنهاد:** یک گزارش «سلامت کدینگ» در تنظیمات یا گزارش‌ها اضافه شود و در تست‌های کدینگ سفارشی پوشش داده شود.

### B-03 — خروجی قبل/بعد مهاجرت حساب‌های Legacy

مهاجرت سطح ۴ پیش‌تحلیل، backup، transaction و audit دارد، اما گزارش قبل/بعد به‌صورت فایل قابل خروجی برای مسئول مالی تولید نمی‌شود.

**پیشنهاد:** خروجی Excel/CSV از نگاشت‌های قبل و بعد، موارد معلق و جمع بدهکار/بستانکار پیش و پس از مهاجرت تولید شود.

### B-04 — فایل گزارش خطای ورود Excel با شماره ردیف

خطاهای ورود گروهی در پیام‌ها و preview دیده می‌شوند، ولی خروجی قابل ذخیره با شماره ردیف اکسل برای اصلاح فایل وجود ندارد.

**پیشنهاد:** در پایان import، فایل گزارش خطا شامل شیت، شماره ردیف اکسل، ستون، مقدار و علت خطا تولید شود.

### B-05 — آزمون‌های property-based برای مرزهای سند

پوشش فعلی برای مقادیر مرزی کافی نیست: اعداد بسیار بزرگ، overflow، تعداد بالای خطوط، مبلغ صفر/منفی و ترکیب‌های مختلف حساب/تفصیلی.

**پیشنهاد:** property-based test برای invariantهای تراز، یکتایی شماره ردیف، محدودیت تعداد خطوط و رفتار اعداد حدی اضافه شود.

### B-06 — آزمون هم‌زمانی چند پنجره

سناریوی دو پنجره واقعی برای ذخیرهٔ هم‌زمان یک سند، تغییر سال مالی، restore و گزارش‌گیری با دیتابیس یکسان وجود ندارد.

**پیشنهاد:** تست یکپارچهٔ Windows/Tauri با دو WebView واقعی یا شبیه‌سازی دقیق state مشترک اضافه شود.

### B-07 — آزمون چاپ و PDF واقعی در WebView2

تست DOM و preview وجود دارد، اما چاپ واقعی، انتخاب printer و ذخیرهٔ PDF در WebView2 آزموده نمی‌شود.

**پیشنهاد:** در Smoke/Integration ویندوز، تولید DOM گزارش، بازشدن پنجرهٔ preview و چاپ/ذخیرهٔ PDF جداگانه بررسی شود.

### B-08 — شناسهٔ عملیات مستقل از عمر dialog

progress/cancel/result عملیات طولانی به dialog و listener متصل است؛ اگر پنجره بسته شود یا listener آزاد شود، نتیجهٔ عملیات قابل بازیابی نیست.

**پیشنهاد:** یک `operation_id` در backend تعریف شود که progress، لغو و نتیجه به آن متصل باشند و پس از بستن dialog نیز وضعیت قابل query باشد.

### B-09 — کنترل یکپارچگی پس از Migration در تست‌ها

`PRAGMA integrity_check` و `PRAGMA foreign_key_check` در مسیر restore وجود دارند، اما پس از هر migration مهم در تست‌ها به‌صورت invariant اجرا نمی‌شوند.

**پیشنهاد:** در تست هر migration، `integrity_check`، `foreign_key_check` و invariantهای حسابداری (جمع بدهکار/بستانکار، شماره ردیف، ساختار حساب) اجرا شوند.

### B-10 — آزمون انتقال و بازیابی `.hacc` روی دستگاه دوم و اعتبارسنجی ACL

رمزنگاری `.hacc` تست واحد دارد، اما انتقال واقعی به دستگاه دوم، بازیابی با رمز صحیح/غلط و بررسی ACL پوشهٔ داده و کلید snapshot در محیط مقصد آزموده نشده است.

**پیشنهاد:** سناریوی end-to-end انتقال backup عادی و `.hacc`، restore روی نصب تازه و بررسی مجوزهای NTFS مستند شود.

### B-11 — آزمون‌های منفی گستردهٔ Excel

پوشش منفی برای ZIP bomb، worksheet خالی یا با ابعاد غیرعادی، سلول merged، تاریخ شمسی نامعتبر، شناسهٔ علمی/float، کد با صفر ابتدایی و فایل خراب کافی نیست.

**پیشنهاد:** مجموعهٔ fixture خراب و دست‌کاری‌شده اضافه شود و تأیید شود خطای parser باعث از دست رفتن دادهٔ ثبت‌شده قبلی یا crash نمی‌شود.

### B-12 — پایداری خطا در فرم و نوع‌های محدود برای ورودی فرمان‌ها

خطاهای backend عمدتاً به‌صورت toast نمایش داده می‌شوند و پس از محو شدن قابل بازیابی نیستند. همچنین برخی ورودی‌های محدود (مانند `mode`) به‌جای enum محدود Rust به‌صورت رشته پذیرفته می‌شوند.

**پیشنهاد:** خطا در خود فرم باقی بماند؛ برای حالت‌های محدود از enum و deserialize سخت‌گیرانه استفاده شود؛ برای همهٔ importها و عملیات مخرب الگوی preview-token یکنواخت شود.

## ۸. موارد مثبت و اصلاحات مهمی که در کد فعلی تأیید شدند

موارد زیر در بررسی کد جاری مشاهده شدند و نباید بدون شواهد تازه به‌عنوان نقص باز ثبت شوند:

1. **اعتبارسنجی در بک‌اند:** فرمان‌های Tauri قواعد مهم را در Rust بررسی می‌کنند؛ کنترل UI تنها مرجع صحت داده نیست.
2. **کنترل دسترسی پنجره‌ها:** توابع `require_window`، `require_preview_window` و `require_main_or_preview_window` در فرمان‌ها برای محدودکردن عملیات به پنجره مجاز استفاده شده‌اند.
3. **محدودیت `open_path`:** فرمان فقط فایل HTML/HTM موجود در allowlist فایل‌های ذخیره‌شده گزارش در نشست جاری را می‌پذیرد؛ مسیر آزاد renderer به‌عنوان برنامه یا فایل دلخواه اجرا نمی‌شود.
4. **حفاظت از عملیات سند:** ذخیره سند دارای کنترل هم‌زمانی با `expected_updated_at`، کلید idempotency و تراکنش SQLite است. وضعیت سند دائمی و دوره مالی نیز در بک‌اند کنترل می‌شود.
5. **کنترل ساختار حساب‌ها:** ارتباط سطح حساب، گروه، parent و تفصیلی در سمت Rust و در بخش‌هایی در triggerهای SQLite کنترل می‌شود.
6. **ورود Excel:** محدودیت حجم فایل، تعداد ردیف/ستون، بودجه ZIP و تعداد خطاها در کد وجود دارد. نرمال‌سازی حروف و ارقام فارسی/عربی نیز در مسیر ورودی پیش‌بینی شده است.
7. **پیش‌نمایش ورود حساب:** preview با توکن کوتاه‌عمر، مسیر canonical، SHA-256 و plan ذخیره‌شده به همان فایل متصل شده است؛ تغییر فایل بعد از preview رد می‌شود.
8. **نگاشت گروه حساب حدسی:** پیش از ثبت گروه‌های حدس‌زده‌شده، تأیید صریح کاربر و ارسال نگاشت نهایی الزامی شده و منبع نگاشت در audit ثبت می‌شود.
9. **لغو ورود گروهی:** بررسی نهایی لغو درست پیش از `tx.commit()` وجود دارد تا درخواست لغو قبل از commit موجب rollback شود.
10. **حفاظت snapshot داخلی:** marker داخل SQLite به‌تنهایی قابل اعتماد نیست؛ manifest بیرونی با HMAC و hash فایل برای تشخیص snapshot داخلی استفاده می‌شود.
11. **Retention:** برای backup عادی، safety backup بازیابی، snapshot حذف گروهی و snapshot مهاجرت حساب سیاست نگهداری محدود وجود دارد (`BACKUP_RETENTION = 30`، `RESTORE_SAFETY_RETENTION = 5`، `PRE_DELETE_RETENTION = 10`، `LEGACY_MIGRATION_SNAPSHOT_RETENTION = 10`)؛ manifest متناظر snapshot همراه فایل حذف می‌شود.
12. **پشتیبان رمزنگاری‌شده:** قالب `.hacc` با AES-256-GCM و Argon2id، allowlist پارامتر KDF و تست رمز اشتباه/دستکاری وجود دارد.
13. **پایداری SQLite:** WAL، foreign key، busy timeout و `synchronous=FULL` فعال‌اند؛ حفظ FULL برای داده‌های حسابداری تصمیم محافظه‌کارانه و قابل دفاعی است.
14. **طبقه‌بندی گزارش:** نگاشت sectionهای گزارش در Rust در یک جدول مرکزی نگهداری می‌شود و تست parity آن را با UI مقایسه می‌کند.
15. **CI چندلایه:** بررسی syntax، ESLint، تست واحد، Playwright، Rust tests، ممیزی وابستگی و build Windows در workflow جداگانه تعریف شده‌اند؛ `desktop-build` به `verify`، `ui-e2e` و `security-audit` وابسته است.
16. **وابستگی‌های حساس:** `calamine 0.38.0` و `tokio 1.54.1` در `Cargo.lock` قفل شده‌اند و نسخه‌های آسیب‌پذیر قبلی در گراف باقی نمانده‌اند.

## ۱۲. نتیجه نهایی

Acc-Rust از نظر معماری کلان، تفکیک UI و بک‌اند، استفاده از Rust برای قواعد مالی، کنترل‌های SQLite، مدیریت تراکنش و پشتیبان‌گیری، پایه مناسبی دارد. تعدادی از ایرادهای مهم گزارش‌های قبلی نیز در کد فعلی واقعاً اصلاح شده‌اند؛ به‌ویژه hardening پارامتر KDF، manifest و HMAC snapshotها، توکن و hash برای preview ورود حساب، تأیید نگاشت حدسی گروه، کنترل لغو پیش از commit، retention و lint فرانت‌اند.

با این حال، مهم‌ترین موضوع جاری **شکست Smoke Test در آخرین build Windows** است که تا تعیین علت و تکرار موفق آزمون باید مانع تأیید build انتشار تلقی شود. ابزار تشخیص این شکست اکنون در کد فراهم شده، اما رفع واقعی آن باید با CI تازه اثبات شود. پس از آن، اولویت‌های مهم عبارت‌اند از تکمیل آزمون یکپارچگی واقعی، دریافت تأیید تخصصی fixture گزارش‌ها، قطعی‌کردن Release امضاشده و تأیید حفاظت فایل‌های backup در محیط نصب واقعی.

**جمع‌بندی:** برای ادامه توسعه و آزمون، وضعیت فنی مناسب است؛ برای انتشار رسمی و استفاده عملیاتی مالی، ابتدا موارد P1 و سپس P2های فوق باید رفع یا با شواهد و پذیرش ریسک مستند تعیین تکلیف شوند.
